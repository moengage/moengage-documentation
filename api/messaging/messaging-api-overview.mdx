The Messaging API sends email to individual recipients that your application specifies. It defines two operations: create a reusable campaign shell, then trigger messages against that shell.

A shell defines the content structure and the campaign settings. Each trigger request specifies one recipient and the values for that send. A single shell therefore supports repeated trigger requests for one message type.

## Prerequisites

<Steps>
  <Step title="Request Access">
    The Messaging API is in early access. Contact your Customer Success Manager to enable it for your workspace.
  </Step>
  <Step title="Create an API Key">
    Create a key with access to the **Campaigns** API. Creating a shell requires **Create & Manage** permissions. Publishing a shell requires **Create, Manage & Publish**.
  </Step>
  <Step title="Configure an Email Connector">
    A shell requires a configured email connector before you publish it.
  </Step>
</Steps>

## Operations

| Operation | Description | Frequency |
| :--- | :--- | :--- |
| Create a shell | Create an Email campaign with `campaign_delivery_type: API_TRIGGERED` that defines the content structure, connector, and delivery controls. Publish the shell to make it triggerable. | Once per message type |
| Trigger a message | Call the trigger endpoint with the shell's `campaign_id`, the recipient, and the values for that send. | Once per recipient |

The following rules apply:

- A trigger request targets an existing published shell. A trigger request never creates a campaign.
- Editing a shell creates a new shell version. Trigger requests do not, so send volume does not affect the shell version.

The trigger endpoint is asynchronous. A `202 Accepted` response confirms that the request is valid and enqueued, and returns a message instance ID. It is not a delivery guarantee. Dispatch occurs after the acknowledgement, and inbox delivery depends on your email provider.

MoEngage sends the message as specified or rejects the request. There is no channel or vendor fallback, and a request that exceeds a limit is rejected rather than queued.

## Endpoints

Shell creation uses the Campaigns API. The Messaging API adds no separate create-campaign endpoint.

| Operation | Endpoint |
| :--- | :--- |
| Create a shell | [Create Campaign](/api/create-campaigns/create-campaign-draft-v5) with `campaign_delivery_type: API_TRIGGERED` |
| Validate a shell | [Validate Campaign](/api/create-campaigns/validate-campaign-v5) |
| Publish or stop a shell | [Update Campaign Status](/api/update-campaigns/update-campaign-status-v5) |
| Edit a shell | [Update Campaign](/api/update-campaigns/update-campaign-v5) |
| Read a shell | [Get Campaign](/api/get-campaign-details/get-campaign-v5) |

## Rate Limits

The default limit on the trigger endpoint is 5,000 requests per minute per workspace. A request targets one recipient, so the limit is also the maximum number of messages you can trigger per minute.

A request that exceeds the limit returns `429` with a `Retry-After` header. MoEngage rejects the request and does not queue it. Every response carries `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset`.

Contact your Customer Success Manager to raise the limit for your workspace.

Creating a shell counts against the `POST /v5/campaigns` limit. Triggering a message against a published shell does not, because the request creates no campaign. See [Rate Limits](/api/rate-limits#messaging).

## Limitations

| Capability | Status |
| :--- | :--- |
| Channels other than Email | Not supported. Use the [Push API](/api/push/push-overview) to send push notifications to individual users. |
| Idempotent retries | Not enforced in this early-access release. The `Idempotency-Key` header is accepted and returned as `response_id`, but MoEngage does not deduplicate on it, so retrying an accepted request sends the message again. Send the header on every request so that no integration change is needed once deduplication is enforced. |
| Campaign reports | Not supported for API-triggered campaigns. |
| Delivery and engagement callbacks | Not supported. Your application receives no per-message outcome notification. |
| Double opt-in | Not supported. A create request that includes `send_only_double_opt_in_users` is rejected. |
| Google annotations | Not supported. |
| Link branding | Not supported. |
| Deep links | Not supported. |
| Brand deduplication | Not supported. A create request that includes `deduplication_attribute` is rejected. |
| Sender address personalization | Not supported. Neither the from address nor the reply-to address accepts personalization. |
| Reply-to unsubscribe and list unsubscribe | Not supported. |
| Segment and filter targeting | Not supported. A create request that includes `segmentation_details` is rejected, and the shell stores an All Users audience. Each trigger request names its own recipient. |
| Scheduling | Not supported. `scheduling_details` is optional, and `delivery_type: ASAP` is accepted with no effect. Any other value is rejected. |
| Throttling | Not supported. `campaign_throttle_rpm` does not apply and no default RPM is applied. The per-request rate limit on the trigger endpoint governs delivery pacing. |
| Maximum-send caps | Not supported. `campaign_audience_limit` and `limit_send_config` do not apply. |
| Do Not Disturb | Not evaluated. MoEngage sends the message regardless of the recipient's DND state, and a create request that sets `bypass_dnd` to `true` is rejected because the flag has no effect. |
| Minimum delay between messages | Not supported with a non-zero value. |
| Pausing a shell | The `PAUSE` and `RESUME` status actions are not supported. Stop the shell instead. |
| Test sends | Test Campaign is not supported. A draft-mode test against a shell returns an error, and an inline-mode test returns no error but does not exercise the shell. Publish the shell and trigger it against a recipient you control instead. |
| File uploads | Not supported. Reference images and attachments by URL. |

For the full list of supported and unsupported fields, see [API-triggered campaigns](/api/campaigns/audience-scheduling-delivery-reference#api-triggered-campaigns).

## FAQs

### Shell Creation

<AccordionGroup>
  <Accordion title="What is a campaign shell?">
    A shell is a reusable email campaign. It defines the content structure with placeholders, the email settings, and the delivery controls. Each trigger request specifies one recipient and the per-send values.
  </Accordion>
  <Accordion title="How do I create a shell?">
    Create it through the Campaigns V5 API with `campaign_delivery_type: API_TRIGGERED`. The shell starts in `DRAFT` status. Validate it, then publish it to make it triggerable. See [Create Campaign](/api/create-campaigns/create-campaign-draft-v5).
  </Accordion>
  <Accordion title="Which campaign components can a shell use?">
    A shell does not accept `segmentation_details`, `scheduling_details`, `trigger_condition`, or `campaign_audience_limit`, because it has no audience and no schedule. Within `delivery_controls`, only `ignore_frequency_capping` and `count_for_frequency_capping` apply. See [API-triggered campaigns](/api/campaigns/audience-scheduling-delivery-reference#api-triggered-campaigns).
  </Accordion>
  <Accordion title="Can I edit a shell after publishing it?">
    Yes. Editing a published shell creates a new shell version, and subsequent trigger requests use the updated content.
  </Accordion>
  <Accordion title="How do I stop a shell from accepting trigger requests?">
    Stop it with the `STOP` status action. After you stop a shell, MoEngage rejects trigger requests against it. A shell supports `PUBLISH` and `STOP` only, so it has no paused state and cannot be resumed. See [Update Campaign Status](/api/update-campaigns/update-campaign-status-v5).
  </Accordion>
  <Accordion title="What are placeholders?">
    Placeholders are named fields in the shell content that each trigger request populates. The shell defines the structure and the trigger request specifies the values.
  </Accordion>
  <Accordion title="Does a shell support control groups?">
    Yes. Set `is_global_control_group_enabled` or `is_campaign_control_group_enabled` in `control_group_details`, and set `campaign_control_group_percentage` to size the campaign control group. Recipients allocated to a control group do not receive the message.
  </Accordion>
  <Accordion title="Does a shell support A/B variations?">
    Yes. Define the variations in `campaign_content.variation_details`, as you would for any other Email campaign.
  </Accordion>
  <Accordion title="How do locales work with a shell?">
    Define the locale variants in `campaign_content.locales`. Each trigger request can set `locale_name` to select one of them. A `locale_name` that the shell does not declare returns `422 UNKNOWN_LOCALE`.
  </Accordion>
  <Accordion title="Can I supply fully resolved content instead of placeholders?">
    Yes. A trigger request can carry a final value, such as HTML that your application has already rendered, instead of a token for MoEngage to resolve. A single request can combine both forms. See [Content for API-triggered shells](/api/campaigns/campaign-content-reference#content-for-api-triggered-shells).
  </Accordion>
</AccordionGroup>

### Triggering Messages

<AccordionGroup>
  <Accordion title="What does the 202 response mean?">
    `202 Accepted` means the request is valid and enqueued for asynchronous dispatch, and it returns a message instance ID. It is not a delivery guarantee. MoEngage sends the message after the acknowledgement, and inbox delivery depends on your email provider.
  </Accordion>
  <Accordion title="Are trigger requests idempotent?">
    Not in this early-access release. MoEngage accepts the `Idempotency-Key` header and returns it as `response_id`, but does not deduplicate on it, so retrying a request that was already accepted sends the message a second time. Track which requests you have sent in your own application, and treat a `202` as confirmation that MoEngage accepted the request.

    Send the header on every request. It is the correlation id between your request and the response, and once deduplication is enforced the same key is honored without any change on your side.
  </Accordion>
  <Accordion title="Can I trigger more than one recipient in a single request?">
    No. `recipients` accepts exactly one identifier, and a request holding more returns `422 RECIPIENT_LIMIT_EXCEEDED`. Call the endpoint once per recipient, within the rate limit.
  </Accordion>
  <Accordion title="What happens when a recipient is in Do Not Disturb?">
    MoEngage sends the message. DND is not evaluated for an API-triggered campaign, so a recipient in a DND window still receives the email. Apply your own suppression before calling the endpoint if you need DND respected.
  </Accordion>
  <Accordion title="How does frequency capping apply?">
    When the shell sets `ignore_frequency_capping` to `false`, MoEngage evaluates your workspace frequency-cap rules for each recipient at send time and drops the message for recipients who have reached their cap. When the shell sets it to `true`, MoEngage bypasses the cap. Use `count_for_frequency_capping` to control whether a send counts toward a recipient's cap. The `minimum_delay_between_two_notification_in_hour` field is not supported with a non-zero value.
  </Accordion>
  <Accordion title="How does MoEngage resolve personalization values?">
    MoEngage resolves a value that contains personalization tokens for each recipient at send time, using the same engine as any other campaign, including user attributes, content blocks, and the Content API. A fully resolved value passes through unchanged. Event-attribute personalization does not apply, because an API-triggered campaign has no triggering event.
  </Accordion>
  <Accordion title="What does an error response look like?">
    Every error carries `error.code`, `error.message`, and `error.target`, naming the field or header responsible. When more than one field fails validation, `error.details[]` lists each failure with its own `target` and `message`. A single-field failure has no `details[]`.
  </Accordion>
  <Accordion title="What happens when I exceed the rate limit?">
    The request returns `429` with a `Retry-After` header. MoEngage rejects the request and does not queue it. Retry after the interval that the header specifies.
  </Accordion>
  <Accordion title="What happens when MoEngage cannot resolve a recipient?">
    MoEngage drops the message and does not retry it, because a retry cannot change the outcome.
  </Accordion>
  <Accordion title="Is recipient resolution case-sensitive?">
    Yes. Send identifiers exactly as the user profile stores them.
  </Accordion>
</AccordionGroup>

### General

<AccordionGroup>
  <Accordion title="Which channels does the Messaging API support?">
    Email only. Use the [Push API](/api/push/push-overview) to send push notifications to individual users.
  </Accordion>
  <Accordion title="Can I get delivery and engagement reports?">
    No. Campaign reporting and per-message delivery callbacks are not available for API-triggered campaigns. Use your email provider's reporting. See [Limitations](#limitations).
  </Accordion>
  <Accordion title="Is there a size limit on the request payload?">
    No limit is enforced, and the endpoint does not reject a request on size. Keep HTML bodies under 102 KB as a guideline, because several email clients clip larger messages.
  </Accordion>
  <Accordion title="Does the Messaging API affect my existing integrations?">
    No. Existing Push API and Campaigns API integrations continue to work without modification, and migration is not required.
  </Accordion>
</AccordionGroup>
