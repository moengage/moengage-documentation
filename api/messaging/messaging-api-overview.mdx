The Messaging API sends email to individual recipients that your application specifies. It uses a two-operation model: create a reusable campaign shell, then trigger messages against that shell.

A shell defines the content structure and the campaign settings. Each trigger request supplies the recipient and the values for that send, so one shell serves every message of a given type.

## Prerequisites

<Steps>
  <Step title="Request Access">
    The Messaging API is in early access. Contact your Customer Success Manager to enable it for your workspace.
  </Step>
  <Step title="Create an API Key">
    Create a key with access to the **Campaigns** API. Creating a shell requires **Create & Manage** permissions. Publishing a shell requires **Create, Manage & Publish**.
  </Step>
  <Step title="Configure an Email Connector">
    A shell requires a configured email connector before you publish it.
  </Step>
</Steps>

## How It Works

| Operation | Description | Frequency |
| :--- | :--- | :--- |
| Create a shell | Create an Email campaign with `campaign_delivery_type: API_TRIGGERED`, carrying the content structure, connector, and delivery controls. Publish the shell to make it triggerable. | Once per message type |
| Trigger a message | Call the trigger endpoint with the shell's `campaign_id`, the recipients, and the values for that send. | Once per send |

This separation has two consequences:

- A trigger request targets an existing published shell. A trigger request never creates a campaign.
- Editing a shell creates a new shell version. Trigger requests do not, so send volume does not affect the shell version.

The trigger endpoint is asynchronous. A `202 Accepted` response confirms that the request is valid and enqueued, and returns a message instance ID. It is not a delivery guarantee. Dispatch occurs after the acknowledgement, and inbox delivery depends on your email provider.

MoEngage sends the message as specified or rejects the request. There is no channel or vendor fallback, and a request that exceeds a limit is rejected rather than queued.

## Endpoints

Shell creation uses the Campaigns API. The Messaging API adds no separate create-campaign endpoint.

| Operation | Endpoint |
| :--- | :--- |
| Create a shell | [Create Campaign](/api/create-campaigns/create-campaign-draft-v5) with `campaign_delivery_type: API_TRIGGERED` |
| Validate a shell | [Validate Campaign](/api/create-campaigns/validate-campaign-v5) |
| Publish or stop a shell | [Update Campaign Status](/api/update-campaigns/update-campaign-status-v5) |
| Edit a shell | [Update Campaign](/api/update-campaigns/update-campaign-v5) |
| Read a shell | [Get Campaign](/api/get-campaign-details/get-campaign-v5) |
| Trigger a message | [Trigger Message](/api/trigger/trigger-message) |

For the components that an `API_TRIGGERED` campaign accepts, see [API-triggered campaigns](/api/campaigns/audience-scheduling-delivery-reference#api-triggered-campaigns). For the content structure, see [Content for API-triggered shells](/api/campaigns/campaign-content-reference#content-for-api-triggered-shells).

## Rate Limits

The default limit on the trigger endpoint is 5,000 requests per minute per workspace. MoEngage counts the limit per API request, not per recipient, so the effective send rate is the request rate multiplied by the number of recipients in each request.

A request that exceeds the limit returns `429` with a `Retry-After` header. MoEngage rejects the request and does not queue it. Every response carries `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset`.

Contact your Customer Success Manager to raise the limit for your workspace.

Creating a shell counts against the `POST /v5/campaigns` limit. Triggering a message against a published shell does not, because the request creates no campaign. See [Rate Limits](/api/rate-limits#messaging).

## Limitations

| Capability | Status |
| :--- | :--- |
| Channels other than Email | Not supported. Use the [Push API](/api/push/push-overview) to send push notifications to individual users. |
| Campaign reports | Not supported for API-triggered campaigns. |
| Delivery and engagement callbacks | Not supported. Your application receives no per-message outcome notification. |
| Control groups | Not evaluated for API-triggered campaigns. |
| A/B testing | Not supported for API-triggered campaigns. |
| Segment and filter targeting | Not supported. Each trigger request names its recipients. |
| Scheduling | Not supported. Per-call scheduling and send-time optimization do not apply. |
| Throttling and maximum-send caps | Not supported. The per-request rate limit governs delivery pacing. |
| File uploads | Not supported. Reference images and attachments by URL. |

## FAQs

### Shell Creation

<AccordionGroup>
  <Accordion title="What is a campaign shell?">
    A shell is a reusable email campaign. It holds the content structure with placeholders, the email settings, and the delivery controls. Each trigger request supplies the recipients and the per-send values, so the same shell serves every message of its type.
  </Accordion>
  <Accordion title="How do I create a shell?">
    Create it through the Campaigns V5 API with `campaign_delivery_type: API_TRIGGERED`. The shell starts in `DRAFT` status. Validate it, then publish it to make it triggerable. See [Create Campaign](/api/create-campaigns/create-campaign-draft-v5).
  </Accordion>
  <Accordion title="Which campaign components can a shell use?">
    A shell does not accept `segmentation_details`, `scheduling_details`, `trigger_condition`, or `campaign_audience_limit`, because it has no audience and no schedule. Within `delivery_controls`, only frequency capping, DND, and minimum delay apply. See [API-triggered campaigns](/api/campaigns/audience-scheduling-delivery-reference#api-triggered-campaigns).
  </Accordion>
  <Accordion title="Can I edit a shell after publishing it?">
    Yes. Editing a published shell creates a new shell version, and subsequent trigger requests use the updated content.
  </Accordion>
  <Accordion title="Can I stop a shell?">
    Yes. A shell moves through `SCHEDULED`, `ACTIVE`, and `STOPPED`. It has no pause or resume state. After you stop a shell, MoEngage rejects trigger requests against it.
  </Accordion>
  <Accordion title="What are placeholders?">
    Placeholders are named slots in the shell content that each trigger request populates. The shell defines the structure and the trigger request supplies the values.
  </Accordion>
  <Accordion title="Can I supply fully resolved content instead of placeholders?">
    Yes. A trigger request can carry a final value, such as HTML that your application has already rendered, instead of a token for MoEngage to resolve. A single request can combine both forms. See [Content for API-triggered shells](/api/campaigns/campaign-content-reference#content-for-api-triggered-shells).
  </Accordion>
</AccordionGroup>

### Triggering Messages

<AccordionGroup>
  <Accordion title="What does the 202 response mean?">
    `202 Accepted` means the request is valid and enqueued for asynchronous dispatch, and it returns a message instance ID. It is not a delivery guarantee. MoEngage sends the message after the acknowledgement, and inbox delivery depends on your email provider.
  </Accordion>
  <Accordion title="What is the Idempotency-Key header?">
    An `Idempotency-Key` (UUID v4) makes retries safe. Replaying the same key with the same request body within the retention window returns the original response and sends no additional message. Reusing the same key with a different body returns `409 CONFLICT`.
  </Accordion>
  <Accordion title="Can I trigger multiple recipients in one request?">
    Yes. A request carries a flat list of recipients of a single identifier type, up to a maximum per request. A request above the maximum returns `422 RECIPIENT_LIMIT_EXCEEDED`. Every recipient in a request receives the same message, with personalization resolved for each recipient.
  </Accordion>
  <Accordion title="Can I mix identifier types in one request?">
    No. Each request declares one `identifier_type`, and every entry in `recipients` must match that type. A request with mixed types returns `400 VALIDATION_FAILED`.
  </Accordion>
  <Accordion title="What happens when a recipient is in Do Not Disturb?">
    When the shell sets `bypass_dnd` to `false`, MoEngage drops the message for a recipient in DND and does not defer or queue it. When the shell sets `bypass_dnd` to `true`, MoEngage sends the message regardless of DND status.
  </Accordion>
  <Accordion title="How does frequency capping apply?">
    When the shell sets `ignore_frequency_capping` to `false`, MoEngage evaluates your workspace frequency-cap rules for each recipient at send time and drops the message for recipients who have reached their cap. When the shell sets it to `true`, MoEngage bypasses the cap. The `minimum_delay_between_two_notification_in_hour` field is a separate control that enforces a minimum interval between two messages from the same shell to the same recipient.
  </Accordion>
  <Accordion title="How does MoEngage resolve personalization values?">
    MoEngage resolves a value that contains personalization tokens for each recipient at send time, using the same engine as any other campaign, including user attributes, content blocks, and the Content API. A fully resolved value passes through unchanged. Event-attribute personalization does not apply, because an API-triggered campaign has no triggering event.
  </Accordion>
  <Accordion title="What happens when I exceed the rate limit?">
    The request returns `429` with a `Retry-After` header. MoEngage rejects the request and does not queue it. Retry after the interval that the header specifies.
  </Accordion>
  <Accordion title="What happens when MoEngage cannot resolve a recipient?">
    MoEngage drops the message for that recipient and does not retry it, because a retry cannot change the outcome. The other recipients in the same request are unaffected.
  </Accordion>
  <Accordion title="Is recipient resolution case-sensitive?">
    Yes. Send identifiers exactly as the user profile stores them.
  </Accordion>
</AccordionGroup>

### General

<AccordionGroup>
  <Accordion title="Which channels does the Messaging API support?">
    Email only. Use the [Push API](/api/push/push-overview) to send push notifications to individual users.
  </Accordion>
  <Accordion title="Can I get delivery and engagement reports?">
    No. Campaign reporting and per-message delivery callbacks are not available for API-triggered campaigns. Use the reporting that your email provider offers. See [Limitations](#limitations).
  </Accordion>
  <Accordion title="Is there a size limit on the request payload?">
    Yes. A request above the maximum payload size returns `413 PAYLOAD_TOO_LARGE`. Keep HTML bodies under 102 KB, because several email clients clip larger messages.
  </Accordion>
  <Accordion title="Does the Messaging API affect my existing integrations?">
    No. Existing Push API and Campaigns API integrations continue to work without modification, and migration is not required.
  </Accordion>
</AccordionGroup>
