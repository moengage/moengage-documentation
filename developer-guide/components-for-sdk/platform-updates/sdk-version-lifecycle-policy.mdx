Every MoEngage SDK major version progresses through four phases: Current, Maintenance, Deprecated, and End-of-Life. This policy defines what support each phase provides, the impact of each transition, and how to stay current.

## 1. How It Works

Support is determined by a version's distance from the current major release, not by calendar dates.

| Version | Phase | Support |
| --- | --- | --- |
| Latest major (T) | Current | New features, bug fixes, security patches, full engineering support |
| One or two majors behind (T‑1, T‑2) | Maintenance | Critical fixes released in the Current major (T) only — not back-ported. No new features. Data flows normally. |
| Three or more majors behind (T‑3+) | Deprecated → End-of-Life | No support, no fixes. Data flows during the Deprecated period, then stops at End-of-Life enforcement. |

<Info>
  **Example (Android):** If 14.x is the current major, 13.x and 12.x are in Maintenance, and 11.x and below are Deprecated. When 15.x ships, 14.x and 13.x enter Maintenance, and 12.x enters Deprecated status.
</Info>

## 2. Deprecated vs. End-of-Life

### Deprecated (T‑3 and Older)

A version enters Deprecated status when it falls three or more major releases behind the current version.

- **Data flows** until End-of-Life enforcement begins in April 2027.
- **Support stops.** MoEngage does not provide debugging, engineering investigation, or support responses for Deprecated versions. All tickets receive an upgrade recommendation.
- **No fixes.** Bug fixes, security patches, and crash fixes are not issued for Deprecated versions. Fixes are released in the Current major only.

### End-of-Life

A Deprecated version reaches End-of-Life when enforcement becomes active (April 2027).

- **Data is rejected.** MoEngage servers reject all API calls from End-of-Life versions with a client-error response. Installs, sessions, and events are not processed.
- **Push and in-app messaging stop.** Delivery is no longer guaranteed.
- **No support of any kind.** Bug reports, security reports, and support tickets are not accepted.

### Why the Distinction Matters

The Deprecated period exists to provide advance notice before data flow is affected. A Deprecated version is not an immediate data loss — it is a defined window to plan and complete an upgrade before enforcement begins.

## 3. What Each Phase Means in Practice

### Current (T)

All forward development occurs on the Current major. New features, OS compatibility updates, security patches, and full engineering support are available. This is the recommended version for all new integrations and active development.

### Maintenance (T‑1, T‑2)

Data flows and is processed normally. When a critical bug, security vulnerability, or broken dependency is identified, the fix is released in the Current major (T) — it is not back-ported. Upgrading to the latest version is required to receive the fix. No new features are added to Maintenance versions.

<Note>
  A critical fix addresses a crash, security vulnerability, or dependency incompatibility that prevents the SDK from functioning correctly. Non-blocking bugs and feature gaps are not back-ported to Maintenance versions.
</Note>

### Deprecated (T‑3 and Older)

Support has ended. Data continues to flow during this period. See [Section 2](#2-deprecated-vs-end-of-life) for the full definition and distinction from End-of-Life.

### End-of-Life

Enforcement is active. MoEngage servers reject all events. Push notifications, in-app messaging, and analytics stop functioning. The SDK continues to run on the device but no longer communicates with MoEngage servers. An upgrade is the only resolution.

## 5. End-of-Life: Impact and Timeline

### Example Scenario

If 30% of Android users are on SDK v11.x (Deprecated), their data flows today. From April 2027, every API call from those devices returns a client-error response. The impact:

- Installs, sessions, and event volume from those users no longer appear in the dashboard.
- Push notifications stop delivering. Journeys dependent on those events fail or stall.
- Attribution data is permanently lost with no retroactive recovery.
- Security vulnerabilities in v11.x are not patched after April 2027.

Upgrading to the current major restores full functionality.

### For Developers

- All events from End-of-Life versions are rejected. API calls return a client-error response.
- The SDK binary continues to run on the device. The app does not crash or freeze.
- Push notification delivery and in-app/in-site message rendering are not guaranteed.
- Bug and security reports against End-of-Life versions are not accepted.
- No security patches are issued. In regulated environments (finance, healthcare, GDPR), an End-of-Life SDK may conflict with internal security compliance requirements.
- On iOS, older SDK versions do not support the latest SKAdNetwork conversion-value models or Privacy Manifest requirements. Attribution accuracy degrades independently of server-side rejection, and this applies before the End-of-Life enforcement date.

### For Marketers and Product Teams

- Campaign metrics (installs, sessions, events, revenue) from users on End-of-Life versions are no longer reported in the dashboard.
- Push and in-app campaign delivery to those users stops.
- User-level attributes and events are no longer ingested.
- Segments, funnels, and journeys dependent on End-of-Life user data under-deliver or stall without an in-product error.
- Data flow stops on a defined, published date — it is not a gradual degradation.

### Enforcement Timeline

Server-side rejection begins April 2027. Deprecated versions continue to send and process data normally until that date.

## 6. Notifications

MoEngage notifies users across multiple channels ahead of every lifecycle transition.

| Channel | Timing | Audience |
| --- | --- | --- |
| SDK runtime log | INFO at 12 months before EOL, escalating to WARN, then ERROR | Developers on the affected version |
| Email | At deprecation announcement, then at 18, 12, 6, and 1 months before EOL | Workspace Admins |
| Dashboard banner | From 6 months before EOL | All workspace users |
| Quarterly SDK newsletter | Every quarter-end | Newsletter subscribers |
| GitHub README / changelog | When a successor major ships | Developers watching the [Android](https://github.com/moengage/android-dependency-catalog), [iOS](https://github.com/moengage/apple-sdk), [React Native](https://github.com/moengage/React-Native), [Flutter](https://github.com/moengage/Flutter-SDK), or [Unity](https://github.com/moengage/MoEngage-Unity-SDK) repositories |

MoEngage publishes a roadmap notice at least 90 days before each planned major SDK release via the developer changelog, email to Workspace Admins, and the SDK's GitHub repositories.

## 7. How to Stay Current

<Steps>
  <Step title="Check Your Version">
    - **Marketers and product owners:** Go to **Dashboard → Settings → SDK Information** to view version distribution by platform across your active user base. If more than 5% of users are on a Deprecated version, coordinate an upgrade with your engineering team.
    - **Developers:** Check the installed package version in your dependency file (`build.gradle` for Android, `Podfile.lock` for iOS, `package.json` for Web and plugin SDKs). Include the running version in production monitoring so you always know what is deployed.
  </Step>
  <Step title="Plan Upgrades Within the Support Window">
    Two full major release cycles are available before a version enters Deprecated status. Plan the next upgrade before the current version reaches T‑2.
  </Step>
  <Step title="Upgrade During the Deprecated Window">
    If a version is already Deprecated, data continues to flow until April 2027. Use this period to complete the upgrade before enforcement begins and data stops permanently.
  </Step>
  <Step title="Follow the Migration Guide">
    When upgrading across major versions, follow the migration guide for that version jump. Where integration changes are required, the guide provides step-by-step instructions. Your CSM or MoEngage Support team can assist with the upgrade path.

    - [Android migration guide](/developer-guide/android-sdk/migration)
    - [iOS migration guide](/developer-guide/ios-sdk/migration/migration-to-sdk-version-9-0-0)
    - [Web migration guide](/developer-guide/web-sdk/migration/standardizing-web-sdk-apis-for-cross-platform-consistency)
  </Step>
</Steps>

## 8. Frequently Asked Questions

<AccordionGroup>
  <Accordion title="Will my app crash or break at End-of-Life?">
    No. The SDK continues to run on the device. MoEngage servers stop accepting data from that version, so analytics, push, and in-app messaging stop functioning — but the app itself is not affected.
  </Accordion>
  <Accordion title="What is the difference between Deprecated and End-of-Life?">
    A Deprecated version (T‑3 or older) no longer receives support or fixes, but data continues to flow until April 2027. End-of-Life means enforcement is active and data is rejected at the server. See [Section 2](#2-deprecated-vs-end-of-life) for details.
  </Accordion>
  <Accordion title="Can I receive a bug fix on a Maintenance version?">
    No. Critical fixes are released in the Current major (T) only and are not back-ported to T‑1 or T‑2. Upgrading to the latest version is required to receive the fix. Migration guides and CSM or Support assistance are available for upgrades requiring integration changes.
  </Accordion>
  <Accordion title="Does pinning to a specific patch version extend the support window?">
    No. Support is determined by the major version. All patches within a Deprecated major share the same Deprecated status and End-of-Life date.
  </Accordion>
  <Accordion title="Can I request an extension during a change freeze or planning cycle?">
    Contact your CSM. The 90-day pre-release notice and staged reminders are designed to support teams with planning constraints. Extension requests are evaluated case by case.
  </Accordion>
  <Accordion title="How do Plugin SDKs (Flutter, React Native, etc.) fit into this policy?">
    Plugin SDKs follow the same lifecycle model. A plugin version does not reach End-of-Life before the native SDK it wraps — the later date applies.
  </Accordion>
  <Accordion title="Does this policy apply to server-side or Data API integrations?">
    No. This policy covers client-side mobile and web SDKs only. Server-side integrations and REST APIs are outside the scope of this policy.
  </Accordion>
  <Accordion title="How will I know when a new major version is planned?">
    MoEngage publishes a roadmap notice at least 90 days before each planned major release via the developer changelog, email to Workspace Admins, and the SDK's GitHub repositories. Watch the [Android](https://github.com/moengage/android-dependency-catalog), [iOS](https://github.com/moengage/apple-sdk), [React Native](https://github.com/moengage/React-Native), [Flutter](https://github.com/moengage/Flutter-SDK), or [Unity](https://github.com/moengage/MoEngage-Unity-SDK) repository on GitHub to receive release notifications.
  </Accordion>
  <Accordion title="The version in use is already Deprecated. Does data stop immediately?">
    No. Deprecated versions continue to send and process data until enforcement begins in April 2027. Use this window to plan and complete an upgrade.
  </Accordion>
</AccordionGroup>

## 9. Policy Summary

| Phase | Data accepted | Fixes provided | New features | Support |
| --- | --- | --- | --- | --- |
| Current (T) | Yes | All | Yes | Full |
| Maintenance (T‑1, T‑2) | Yes | Critical, in Current only | No | Limited |
| Deprecated (T‑3+) | Yes, until April 2027 | No | No | No |
| End-of-Life | No — data rejected | No | No | No |
