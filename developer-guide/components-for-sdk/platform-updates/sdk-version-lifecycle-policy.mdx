Every MoEngage SDK major version moves through a predictable lifecycle — Current, Maintenance, Deprecated, and End-of-Life. This policy defines what level of support each phase provides, when transitions occur, and what actions to take at each stage.

MoEngage maintains every supported SDK version so your integration continues to work as your app grows. Staying on a supported version means reliable data flow, timely security updates, and full access to engineering support. Predictable timelines and advance notice at every stage allow you to plan upgrades without disrupting your users or your data.

## 1. How It Works

Support is based on a version's distance from the current major release, not on calendar dates. This makes the lifecycle predictable: you always know where your version stands.

| Your version is | Phase | What you get |
| --- | --- | --- |
| The latest major (T) | Current | New features, all bug fixes, security patches, full support |
| One or two majors behind (T‑1, T‑2) | Maintenance | If you encounter a crash, security issue, or broken dependency, the fix is released in the Current major (T). You must upgrade to receive it — fixes are not back-ported to T‑1 or T‑2. No new features. Data still flows normally. |
| Three or more majors behind (T‑3 and older) | Deprecated → End-of-Life | No support, no fixes. Data still flows during the Deprecated period, then stops when End-of-Life enforcement begins. Plan your upgrade during this window. |

<Info>
  **Example (Android):** If 14.x is the current major, then 13.x and 12.x are in Maintenance, and 11.x and below are Deprecated (moving to End-of-Life when enforcement begins). When 15.x ships, 14.x and 13.x enter Maintenance, and 12.x enters Deprecated status.
</Info>

## 2. Deprecated vs. End-of-Life

MoEngage distinguishes between Deprecated and End-of-Life SDK versions to clarify the level of support and the impact on data measurement. A version can be Deprecated before it reaches End-of-Life, and the consequences at each stage are different.

### Deprecated (T‑3 and Older)

A version enters Deprecated status when it falls three or more major releases behind the current version (T‑3 and older).

- **Data still flows.** Deprecated versions can still send data to MoEngage, and events are processed normally until enforcement begins in April 2027.
- **Support stops.** MoEngage no longer provides debugging, engineering investigation, or support-channel responses for Deprecated versions. The response to any ticket originating from a Deprecated version is an upgrade recommendation.
- **Fix delivery stops.** Bug fixes, security patches, and crash fixes are not provided for Deprecated versions — even critical ones. Fixes ship forward into the Current major only.
- **Plan your upgrade during this period.** Data continues to flow while a version is Deprecated, giving you time to upgrade before enforcement begins and data stops.

### End-of-Life

A Deprecated version reaches End-of-Life when enforcement becomes active (April 2027). At this point, all SDK functionality stops: data collection is halted, push delivery ceases, and in-app messaging no longer renders.

- **Data is rejected.** Installs, sessions, and in-app events are no longer measured. Events from End-of-Life versions will receive a client-error response — the SDK will attempt to send API calls as usual, but MoEngage servers will reject them, and the data will not be processed.
- **Push and in-app messaging stop.** Push notification delivery and in-app/in-site message rendering are no longer guaranteed for End-of-Life versions.
- **No support of any kind.** Bug reports, security reports, and support tickets are not accepted against End-of-Life versions.

### Why the Distinction Matters

The Deprecated period — between when a version enters T‑3 status and when enforcement begins — is a planned transition window. It gives you time to upgrade before data flow is affected. Planning your upgrade during this window ensures a smooth transition with no gap in measurement.

## 3. What Each Phase Means in Practice

### Current (T)

All forward development occurs on the Current major. You get new features, performance improvements, OS compatibility updates, and full access to MoEngage support. This is the recommended version for all new integrations and ongoing active development.

### Maintenance (T‑1, T‑2)

Your data continues to flow and be processed normally. When a crash-level bug, security vulnerability, or broken transitive dependency is identified, MoEngage investigates and delivers the fix in the Current major (T) only — it is not back-ported to T‑1 or T‑2. To receive the fix, you need to upgrade to the latest version. No new features or non-critical changes are made to Maintenance versions.

<Note>
  A critical fix addresses a crash, security vulnerability, or dependency incompatibility that prevents the SDK from functioning correctly. Non-blocking bugs and feature gaps are not back-ported to Maintenance versions.
</Note>

### Deprecated (T‑3 and Older)

Your version is three or more majors behind the current release. Engineering investigation, debugging, and patch delivery are no longer available. Data still flows during this period. Use this window to upgrade before enforcement begins.

### End-of-Life

Enforcement is active. MoEngage servers reject all events from End-of-Life versions. Push, in-app messaging, and analytics stop delivering. The SDK on the device does not crash or freeze — it stops communicating with MoEngage servers. Upgrading to the current major restores full functionality.

## 5. End-of-Life: What Happens and What to Expect

This section covers both the technical impact (for developers) and the business impact (for marketers and product teams) when a version reaches End-of-Life and enforcement is active.

### A Worked Scenario

Suppose 30% of your Android users are on SDK v11.x, which is in Deprecated status. Today, their data still flows. When enforcement begins in April 2027, the SDK on those devices will continue to run, but every API call to MoEngage will be rejected with a client-error response. The impact:

- Approximately 30% of your Android installs and event volume stop appearing in the dashboard, with no warning shown to the user.
- Push notifications sent to those users stop delivering. Journeys that depend on those events will fail or stall.
- Attribution data for those users cannot be recovered retroactively.
- Security vulnerabilities discovered in v11.x after April 2027 are not patched.

Upgrading to the current major restores full functionality.

### For Developers

- MoEngage servers reject all events from End-of-Life versions. API calls return a client-error response.
- The SDK binary on the device continues to run — the app does not crash or freeze.
- Push notification delivery and in-app/in-site message rendering are no longer guaranteed.
- Bug reports and security reports against End-of-Life versions are not accepted.
- No security patches are issued for End-of-Life versions. If your app operates in a regulated environment (finance, healthcare, or GDPR-sensitive), running an End-of-Life SDK may not satisfy your internal security requirements.

### For Marketers and Product Teams

- Campaign metrics drop to zero for users on End-of-Life SDK versions. Installs, sessions, events, and revenue data from those users stop appearing in the dashboard.
- Push and in-app campaign delivery to those users stops or becomes unreliable.
- User-level data (attributes, events) from those users is no longer ingested.
- Segments, funnels, and journeys that depend on events from End-of-Life users will under-deliver or stall with no in-product error.
- Attribution accuracy on iOS degrades before End-of-Life. Older iOS SDK versions do not support the latest SKAdNetwork conversion-value models and Privacy Manifest changes. Attribution for those versions will be rejected at ingestion and will be structurally less accurate. This is an iOS-specific concern driven by Apple's privacy framework requirements; Android attribution follows the standard End-of-Life data rejection timeline.
- Data flow stops on a specific, published date, giving your team a clear target for upgrade planning.

### Enforcement Timeline

Data-plane enforcement (server-side rejection) starts April 2027. Until then, Deprecated versions continue to send and process data normally. This window gives every team time to plan and complete their upgrade on their own schedule.

## 6. How We Notify You

Notifications are layered across multiple channels so that no deprecation or End-of-Life is a surprise. Subscribe to at least one to stay informed.

| Channel | Timing | Who receives it |
| --- | --- | --- |
| SDK runtime log | INFO at 12 months before EOL, escalating to WARN, then ERROR | Developers running the affected version |
| Email | At the deprecation announcement, then 18 / 12 / 6 / 1 months before EOL | Workspace Admins |
| Dashboard banner | From 6 months before EOL | Anyone using a workspace on an affected version |
| Quarterly SDK newsletter | Every quarter-end, starting with the policy launch | Newsletter subscribers |
| GitHub README / changelog | When a successor major ships | Developers watching the [Android](https://github.com/moengage/android-dependency-catalog), [iOS](https://github.com/moengage/apple-sdk), [React Native](https://github.com/moengage/React-Native), [Flutter](https://github.com/moengage/Flutter-SDK), or [Unity](https://github.com/moengage/MoEngage-Unity-SDK) repositories |

MoEngage commits to publishing a roadmap notice at least 90 days before each planned major SDK release, on the developer changelog, by email to Workspace Admins, and on the SDK's GitHub repository.

## 7. How to Stay Current

<Steps>
  <Step title="Check Your Version">
    - **Marketers and product owners:** Go to **Dashboard → Settings → SDK Information** to see the version distribution across your active user base by platform. If more than 5% of users are on a Deprecated version, prioritize the upgrade with your engineering team.
    - **Developers:** Check the installed package version in your dependency file (`build.gradle` for Android, `Podfile.lock` for iOS, `package.json` for Web and plugin SDKs). Log this value to your monitoring so you always know what is in production.
  </Step>
  <Step title="Plan Upgrades Within the Support Window">
    You have two full release cycles to upgrade before your version enters Deprecated status. Plan the next upgrade before the current version reaches T‑2.
  </Step>
  <Step title="Act During the Deprecated Window">
    If your version is already Deprecated, data is still flowing. Use this window to upgrade before enforcement begins in April 2027.
  </Step>
  <Step title="Follow the Migration Guide">
    When upgrading across major versions, use the migration guide for that version jump. Where the jump is straightforward, you can upgrade directly. Where integration changes are required, the guide walks through each step.

    - [iOS migration guide](/developer-guide/ios-sdk/migration/migration-to-sdk-version-9-0-0)
    - [Web migration guide](/developer-guide/web-sdk/migration/standardizing-web-sdk-apis-for-cross-platform-consistency)
  </Step>
</Steps>

## 8. Frequently Asked Questions

<AccordionGroup>
  <Accordion title="Will my app crash or break at End-of-Life?">
    No. MoEngage servers stop accepting data from that version; the SDK on the device continues to run. The app functions normally — MoEngage analytics, push, and in-app events stop delivering.
  </Accordion>
  <Accordion title="What is the difference between Deprecated and End-of-Life?">
    A Deprecated version has fallen three or more majors behind the current release. Support has stopped, but data still flows until enforcement begins (April 2027). End-of-Life means enforcement is active — data is rejected at the server. The Deprecated period is your window to upgrade before data flow stops. See [Section 2](#2-deprecated-vs-end-of-life) for full details.
  </Accordion>
  <Accordion title="Can I get a bug fix on the Maintenance version I am running?">
    No. When MoEngage investigates and resolves a critical issue, the fix is released in the Current major (T) only — it is not back-ported to T‑1 or T‑2. To receive the fix, upgrade to the latest version. If the upgrade requires integration changes, a migration guide is available, and your Customer Success Manager (CSM) or Support team can help you through it.
  </Accordion>
  <Accordion title="Does pinning to a specific patch version extend my support window?">
    No. Support is anchored to the major version, not the patch. All patches of a Deprecated major (for example, 11.0.1, 11.2.3) share the same Deprecated status and the same End-of-Life date.
  </Accordion>
  <Accordion title="Can I get an extension if we are in a change freeze or have annual planning cycles?">
    Contact your CSM. The 90-day pre-release notice and multi-stage reminders are designed to help teams plan around freezes. Extensions are evaluated case by case.
  </Accordion>
  <Accordion title="What if our app uses a Plugin SDK (Flutter, React Native, etc.)?">
    Plugin SDKs follow the same lifecycle model, with one additional safeguard: a plugin never reaches End-of-Life before the native SDK it wraps. The later date always wins.
  </Accordion>
  <Accordion title="Does this policy apply to server-side or Data API integrations?">
    No. This policy covers client-side mobile and web SDKs only. Server-side and REST APIs are outside the scope of this policy.
  </Accordion>
  <Accordion title="How do we know when a new major version is coming?">
    MoEngage publishes a roadmap notice at least 90 days before each planned major release. Subscribe to the SDK newsletter or watch the SDK repository on GitHub to receive these notices.
  </Accordion>
  <Accordion title="We are already on a Deprecated version. Will our data stop immediately?">
    No. Deprecated versions continue to send and process data until enforcement begins in April 2027. Use this window to plan and complete your upgrade.
  </Accordion>
</AccordionGroup>
