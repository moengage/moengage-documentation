---
title: "Install/Update differentiation"
description: "Differentiate between app installs and updates in your iOS app using the MoEngage appStatus API."
---

Since you might integrate us when your app is already on the App Store, we would need to know whether your app update would be an actual **UPDATE** or an **INSTALL**. Have a logic in place to differentiate between the two, and use the methods below to let the SDK know about the same:

<CodeGroup>

```swift Swift wrap
//For Fresh Install of App
MoEngageSDKAnalytics.sharedInstance.appStatus(.install)

// For Existing user who has updated the app
MoEngageSDKAnalytics.sharedInstance.appStatus(.update)
```


```objective-c Objective C
//For Fresh Install of App
[[MoEngageSDKAnalytics sharedInstance]appStatus:MoEngageAppStatusInstall];

// For Existing user who has updated the app
[[MoEngageSDKAnalytics sharedInstance]appStatus:MoEngageAppStatusUpdate];
```

</CodeGroup>

<Note>
  Starting with iOS SDK [11.0.0](/release-notes/sdks/ios#22nd-july-2026), `appStatus(_:)` returns a typed task object ([`MoEngageSetAppStatusTask`](https://moengage.github.io/ios-api-reference/Classes/MoEngageSetAppStatusTask.html)) instead of `Void`. The return value is annotated `@discardableResult`, so direct calls like the ones above compile unchanged.
</Note>

Attach `onSuccess` and `onFailure` to the returned task to confirm the SDK recorded the app status:

<CodeGroup>

```swift Swift wrap
MoEngageSDKAnalytics.sharedInstance.appStatus(.install)
    .onSuccess { result in
        // The SDK recorded the app status.
    }
    .onFailure { failure in
        print("App status failed: \(failure.reason) - \(failure.message)")
    }
```

```objective-c Objective C wrap
MoEngageSetAppStatusTask *task = [[MoEngageSDKAnalytics sharedInstance] appStatus:MoEngageAppStatusInstall];

[task onSuccess:^(id _Nonnull result) {
    // The SDK recorded the app status.
}];

[task onFailure:^(MoEngageRequestFailure * _Nonnull failure) {
    NSLog(@"App status failed: %@ - %@", failure.reason, failure.message);
}];
```

</CodeGroup>

Handlers run on the main thread, and registering a second handler of the same kind replaces the first. `onFailure` receives a [`MoEngageRequestFailure`](https://moengage.github.io/ios-api-reference/Classes/MoEngageRequestFailure.html): `reason.code` carries a [shared failure code](https://moengage.github.io/ios-api-reference/Classes/MoEngageRequestFailureReason/Code.html) — `sdkNotInitialized` and `networkError` are the most likely here — and `message` describes the failure. Swift callers can `await` the task's `result()` method instead of attaching handlers.
