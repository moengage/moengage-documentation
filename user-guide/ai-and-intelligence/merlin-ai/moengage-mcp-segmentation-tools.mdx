The [MoEngage MCP server](/user-guide/ai-and-intelligence/merlin-ai/moengage-mcp-server) (MCP stands for Model Context Protocol) includes a set of **segmentation tools** that let your AI assistant work with audiences end to end: discover the right events and attributes, build and validate filters, create reusable custom segments, estimate audience size (with or without creating a segment), and check whether a specific user belongs to a segment in real time.

This page describes each segmentation tool: what it does, when to use it, its parameters, and known caveats. For connector setup, authentication, and the full tool catalog, see [MoEngage MCP Server and Connector](/user-guide/ai-and-intelligence/merlin-ai/moengage-mcp-server).

If you are new to MoEngage segmentation concepts, start with [Basics of Segmentation](/user-guide/segment/basics-of-segmentation/basics-of-segmentation). MoEngage also offers [Merlin AI Segment Assist](/user-guide/ai-and-intelligence/merlin-ai/merlin-ai-segment-assist), an AI-powered segment builder inside the dashboard. The MCP tools on this page let any connected AI assistant do the same kind of work through natural-language conversation, outside the dashboard.

<Info>
  You interact with these tools by describing what you want in plain language. Your AI assistant handles the parameters and JSON shown on this page. Use this reference to understand exactly what is happening, or to troubleshoot an unexpected result.
</Info>

<Warning>
  **Always resolve internal names first.** Segment filters must use the exact **internal** (platform) names of events and attributes (for example, `moe_city`, not the dashboard display name "City"). A display name is **often accepted when you create a segment or query**. A partial safety-net check catches some cases (see [`create_custom_segment`](#create-and-browse-segments)), but not all. When it isn't caught, the count job later **fails with no error reason**. Before creating or counting anything, resolve names with `find_events`, `find_user_attributes`, and `find_event_attributes`, and always use the returned `name` field, never `readable_name`.
</Warning>

## How the Tools Fit Together

Together, these tools take a plain-English request from discovery through a validated, reachable audience.

<Steps>
  <Step title="Discover">
    Resolve the exact internal names with `find_events`, `find_user_attributes`, and `find_event_attributes`, and explore stored values with `get_value_suggestions`.
  </Step>
  <Step title="Validate">
    Run `deep_validate_segment_filters` on the filter set to catch bad names, data types, or operators before anything is created.
  </Step>
  <Step title="Confirm Intent">
    Use `describe_segment_filters` to turn the filter JSON into a plain-English sentence and confirm it matches what you asked for.
  </Step>
  <Step title="Create or Count">
    Create a reusable segment with `create_custom_segment`, or run a one-off count without creating anything using `create_recent_query`.
  </Step>
  <Step title="Measure">
    Get the user count and channel reachability with `start_segment_count` + `poll_segment_count` (for saved segments) or by polling the recent query.
  </Step>
</Steps>

### Worked Example

A complete request follows this sequence, using the Mumbai example shown throughout this page:

1. **Resolve names**: `find_user_attributes("city")` returns `moe_city`; `find_events("purchase")` returns `Product Purchased`.
2. **Validate**: `deep_validate_segment_filters` checks the draft filter and returns `is_valid: true`.
3. **Create**: `create_custom_segment` creates the segment and returns a `segment_id`.
4. **Measure**: `start_segment_count` returns a `tracking_id`; `poll_segment_count` returns the `user_count` and channel reachability once the job finishes.

## Discover Events, Attributes, and Values

Use these tools before building any filter. They return top-ranked matches with confidence scores, never the full catalog.

### `find_events`

Finds user events (actions) matching a natural-language term (for example, "purchase" or "app opened"). Event names vary per workspace, so the assistant should never guess them.

| Parameter | Required | Description |
| --- | --- | --- |
| `query` | Yes | Natural-language description of the event (for example, "purchase", "checkout"). |
| `limit` | No | Maximum results, 1–50 (default 10). |

Returns ranked matches with `name`, `readable_name`, `category`, a relevance `score`, and a `confident` flag. Use the returned `name` as `action_name` in filters.

<Note>
  Events with no activity in the last **60 days** are excluded from results. If no result is marked `confident`, rephrase or broaden the search term.
</Note>

### `find_user_attributes`

Finds user (profile) attributes matching a natural-language term (for example, "city" or "lifetime value"). Returns the internal `name` (for example, `moe_city`), the display `readable_name`, and the attribute's `data_type`, which determines the operators you can use in a filter.

| Parameter | Required | Description |
| --- | --- | --- |
| `query` | Yes | Natural-language description of the attribute (for example, "city", "signup date"). |
| `limit` | No | Maximum results, 1–50 (default 10). |

### `find_event_attributes`

Finds the attributes (properties) of a specific event (for example, the "amount" attribute of a "Product Purchased" event). Resolve the exact event name with `find_events` first.

| Parameter | Required | Description |
| --- | --- | --- |
| `event_name` | Yes | Exact event name from `find_events` (for example, "Product Purchased"). |
| `query` | Yes | Natural-language description of the attribute (for example, "amount", "category"). |
| `limit` | No | Maximum results, 1–50 (default 10). |

<Note>
  When no confident match is found, the response includes a `hint` and `all_attributes` (the complete list of attributes on that event), so the right attribute can be picked directly. Do not switch to a different event because its name appears to be a better literal match.
</Note>

### `get_value_suggestions`

Fetches up to **5,000 distinct stored values** for a user or event attribute, useful for checking which values exist (for example, which cities) before writing an equality filter.

| Parameter | Required | Description |
| --- | --- | --- |
| `attribute_name` | Yes | Internal attribute name (the `name` from `find_user_attributes` / `find_event_attributes`). |
| `data_type` | Yes | Stored data type: `string` (text), `double` (number), `array_string` (list of text values), `array_double` (list of numbers), `array_object` (list of structured records), or `object` (a structured record). |
| `action` | No | Exact event name from `find_events` when the attribute is an event attribute. Omit for user attributes. |
| `prefix` | No | Only return values starting with this prefix (for example, "ele" returns "electronics"). |
| `node_attribute_name` | No | For `array_object` attributes, the child attribute to resolve values for. |
| `node_data_type` | No | Data type of the child attribute (required with `node_attribute_name`). |

**Example prompt:** _"What values does the `moe_city` attribute have that start with 'San'?"_

For an `array_object` attribute, add `node_attribute_name` and `node_data_type` to resolve values for a child field. For example, `attribute_name: cart_items`, `data_type: array_object`, `node_attribute_name: category`, and `node_data_type: string` return the category values found inside each cart item.

## Describe and Validate Filters

Segment filters are JSON structures (the same filter format across `create_custom_segment`, `create_recent_query`, and the validation tools). These two tools help you check a filter set **before** anything is created.

### `describe_segment_filters`

Turns a segment filter set into a **plain-English sentence**, so you can confirm what a filter means before creating a segment or query, or explain the logic of an existing segment (pass in the filters returned by `get_segment`).

| Parameter | Required | Description |
| --- | --- | --- |
| `included_filters` | Yes | Filter group of users to include: `{"filter_operator": "and"\|"or"\|"difference", "filters": [...]}`. |
| `excluded_filters` | No | Filter group of users to exclude. Same shape. |
| `validation_required` | No | When `true`, the filter set is validated before it is described (default `false`). |

Returns `{description: "<plain-English sentence>"}`.

<Note>
  Filter items use the same shapes `create_custom_segment` accepts (see the [filter types and example](#create-and-browse-segments)): a `user_attributes` filter is **flat**, with `filter_type`, `name`, `data_type`, `operator`, and `value` at the top level, while an `actions` filter nests `attributes`, `execution`, and `primary_time_range` under `action_name`. Unlike `create_custom_segment`, the `filter_operator` here also accepts `difference`. Display names in the filters produce a misleading description. Resolve internal names first.
</Note>

### `deep_validate_segment_filters`

Runs **deep (semantic) validation** of a filter payload against your workspace's live metadata catalog, checking attribute existence, data types, and operator compatibility beyond basic structural checks. Run it before `create_custom_segment` or `create_recent_query` to catch a bad attribute or event name up front instead of a silent count-job failure later.

| Parameter | Required | Description |
| --- | --- | --- |
| `included_filters` | Yes | Filter group of users to include. Same filter format `create_custom_segment` accepts. |
| `excluded_filters` | No | Filter group of users to exclude. |

<Warning>
  The call returns **HTTP 200** (the status code that normally signals success) **whether or not the filters are valid**. Always check the `is_valid` field in the response, not the status code. When invalid, `errors` lists each failure as `{path, field, message}`, where `path` is the <Tooltip tip="A way of pointing to a nested field using dots, like included_filters.filters.0.name.">dot-notation</Tooltip> location of the failing filter node (for example, `included_filters.filters.0.name`).
</Warning>

## Create and Browse Segments

Use these tools to create a segment once and reuse it across campaigns, or to inspect one that already exists. This creates the same kind of segment you would build manually with [Rule-Based (Filter) Segments](/user-guide/segment/segment-operations/rule-based-filter-segments) in the dashboard.

### `create_custom_segment`

Creates a new **filter-based custom segment** in the workspace. The segment type is fixed to filter-based (ELASTIC_SEARCH) and the source to API. Neither can be set by the caller.

| Parameter | Required | Description |
| --- | --- | --- |
| `name` | Yes | Segment name. Must be unique in the workspace, maximum 200 characters, no HTML. `All Users` is reserved. |
| `included_filters` | Yes | Filter group of users to include: `{"filter_operator": "and"\|"or", "filters": [...]}` with a non-empty `filters` array. |
| `description` | No | Free-text description. |
| `excluded_filters` | No | Filter group: users matching these are excluded even if they match `included_filters`. |

Each filter in a filter group is one of four types:

- `user_attributes`: a flat condition on a user attribute, with `filter_type`, `name`, `data_type`, `operator`, and `value` at the top level of the filter object. Valid operators depend on the attribute's `data_type`; for text equality, the operator is `is` (not `equals`).
- `actions`: a condition on an event, keyed by `action_name`. The `attributes` key holds event-property conditions (in the same flat shape as `user_attributes` filters) and is required even when empty: pass `{"filter_operator": "and", "filters": []}`. The optional `execution` object sets an execution count (`{"type": "atleast" | "exactly" | "atmost", "count": <n>}`), and the optional `primary_time_range` object sets a time window (its operator key is `type`, accompanied by `value`, `value_type`, and `period_unit`).
- `custom_segments`: membership in another segment: `{"filter_type": "custom_segments", "id": "<segment_id>", "name": "<segment_name>"}`. The reference field is `id` (as returned by `list_segments`), not `segment_id`.
- `nested_filters`: one level of AND/OR nesting: `{"filter_type": "nested_filters", "filter_operator": "and", "filters": [...]}`. Only one level is supported; deeper nesting is rejected.

The example below shows `user_attributes` and `actions` filters. Whatever the filter mix, run `deep_validate_segment_filters` on the finished filter set before creating anything; it verifies names, data types, and operator compatibility against your workspace's live catalog.

**Example:** Users in Mumbai who purchased at least 3 times in the last 30 days, excluding anyone who refunded a purchase in the last 90 days:

```json
{
  "name": "Mumbai frequent purchasers",
  "included_filters": {
    "filter_operator": "and",
    "filters": [
      {
        "filter_type": "user_attributes",
        "name": "moe_city",
        "data_type": "string",
        "operator": "is",
        "value": "Mumbai"
      },
      {
        "filter_type": "actions",
        "action_name": "Product Purchased",
        "executed": true,
        "attributes": { "filter_operator": "and", "filters": [] },
        "execution": { "type": "atleast", "count": 3 },
        "primary_time_range": {
          "type": "inTheLast",
          "value": 30,
          "value_type": "relative_past",
          "period_unit": "days"
        }
      }
    ]
  },
  "excluded_filters": {
    "filter_operator": "or",
    "filters": [
      {
        "filter_type": "actions",
        "action_name": "Product Refunded",
        "executed": true,
        "attributes": { "filter_operator": "and", "filters": [] },
        "execution": { "type": "atleast", "count": 1 },
        "primary_time_range": {
          "type": "inTheLast",
          "value": 90,
          "value_type": "relative_past",
          "period_unit": "days"
        }
      }
    ]
  }
}
```

To target users who did **not** perform an event, do not use `executed: false`.

<Warning>
  Setting `executed: false` on an `actions` filter is **silently ignored**: the query runs without error and the filter is evaluated as a positive "did the event" condition. Express a negative event condition in one of two ways: place a positive `actions` filter in `excluded_filters` (as the refund exclusion in the example above does), or keep the filter in `included_filters` with `"execution": {"type": "atmost", "count": 0}`. To confirm the negation was applied, pass the filters to `describe_segment_filters` and check that the description reads as a "did not" condition.
</Warning>

<Warning>
  Attribute and event names are **not validated at create time** by default. A wrong name is accepted, the segment is created, and the segment count later fails with **no error reason**. As a partial safety net, the tool checks user-attribute filter names against the workspace catalog before creating and rejects a recognized display name (or wrongly cased internal name), but this check fails open when the catalog is unavailable, so it isn't guaranteed. Resolve names with the [discovery tools](#discover-events-attributes-and-values) first and validate with `deep_validate_segment_filters`. Don't rely on the safety net.
</Warning>

Beyond name resolution, a few other create-time errors are common:

<Note>
  Common errors: `409` (Conflict) when the segment name already exists; `400` (Bad Request) when filters are malformed (the error is generic, without field-level detail; re-check the filter structure rather than retrying variations); `413` (Payload Too Large) when the filter query exceeds size or depth limits. On `actions` filters, the `attributes` key is required even when empty: pass `{"filter_operator": "and", "filters": []}`. A frequent cause of a `400` on `user_attributes` filters is the operator `equals`, which the API rejects; use `is` for text equality.
</Note>

### `list_segments`

Lists the custom segments in the workspace, **paginated**, with an optional partial-match name filter. Returns Filter (ELASTIC_SEARCH) and File type segments; Warehouse, Analytics, and Composite segments are excluded.

| Parameter | Required | Description |
| --- | --- | --- |
| `name` | No | Partial-match filter on segment name. |
| `page` | No | Page number, 1-based (default 1). |
| `page_size` | No | Segments per page, 1–100 (default 10). |

Results contain metadata only (`id`, `name`, `type`, `source`, timestamps). Use `get_segment` to fetch a segment's filter definition.

### `get_segment`

Retrieves the full details of one segment by its ID, including the complete `included_filters` / `excluded_filters` tree. The returned filter tree uses the same format `create_custom_segment` accepts, so it can be read, edited, and resubmitted as a new segment.

| Parameter | Required | Description |
| --- | --- | --- |
| `segment_id` | Yes | The segment's 24-character ID (as returned by `list_segments` or `create_custom_segment`). |

<Note>
  For file-based or cohort-import segments, only metadata is returned; there is no filter tree.
</Note>

## Count Users and Check Reachability

Counting is **asynchronous**: one tool starts the job, another polls for the result.

### `start_segment_count`

Starts an async job that computes the **user count** and <Tooltip tip="Whether MoEngage can message the user on that channel (for example, whether they have a valid push token or a subscribed email address).">channel reachability</Tooltip> (push, email, SMS, WhatsApp) for a saved segment.

| Parameter | Required | Description |
| --- | --- | --- |
| `segment_id` | Yes | The segment's 24-character ID. |
| `callback_url` | No | Webhook URL to notify when the job completes. |

Returns a `tracking_id` and a `status`. Results are cached server-side for **15 minutes**. If a fresh result already exists, the response has `served_from_cache: true` and `status: "finished"` immediately; otherwise poll with `poll_segment_count`.

### `poll_segment_count`

Polls the result of a count job started by `start_segment_count`. Repeat until `status` is `finished` (result ready) or `failure`.

| Parameter | Required | Description |
| --- | --- | --- |
| `segment_id` | Yes | The segment's 24-character ID. |
| `tracking_id` | Yes | The `tracking_id` returned by `start_segment_count`. |
| `channels` | No | Comma-separated channels to include in reachability (for example, `push,email`). Omit for all channels. |
| `push_platforms` | No | Comma-separated push platforms for a per-platform breakdown (for example, `ANDROID,iOS,web`). |

When finished, the response contains `user_count` and a `reachability_count` breakdown per channel. Typical jobs finish in under 30 seconds; the assistant should wait a few seconds between polls.

<Warning>
  A count that ends in `failure` **without an error reason** almost always means a filter in the segment uses a display name instead of the internal attribute or event name. Fix the segment's filters using the [discovery tools](#discover-events-attributes-and-values) and `deep_validate_segment_filters`.
</Warning>

## Count an Audience Without Creating a Segment

To estimate audience size for a filter set **without saving a segment**, use a recent query: an ad-hoc, asynchronously executed audience query.

### `create_recent_query`

Creates and asynchronously runs an audience query. Returns a query ID (`rq_id`) immediately; the count is fetched by polling `get_recent_query`.

| Parameter | Required | Description |
| --- | --- | --- |
| `included_filters` | Yes, when `query_type` is `filter` | Filter group of users to include, the same filter format `create_custom_segment` uses. |
| `excluded_filters` | No | Filter group of users to exclude. |
| `extra_filters` | No | Additional user-attribute query layered on top. |
| `platforms` | No | Restrict results to platforms (for example, `["ANDROID", "iOS", "web"]`). |
| `installed` | No | Install-status filter: `installed` or `uninstalled`. |
| `reachability` | No | Reachability request: one key per channel (`push`, `email`, `sms`, `whatsapp`), each mapping to a channel configuration object. An empty object (`{"push": {}}`) is valid; a channel key can also carry configuration, such as a platform list for push. See the note below on how this parameter is currently applied. |
| `emails` | No | Email recipients notified when the query completes. |
| `channel_source` | No | Channel source scope. Queries created through this tool currently have their channel source set to `MCP` by the server. |
| `cs_id` | No | Associate the run with an existing custom segment's ID. |
| `query_type` | No | `filter` (default), `merlin`, or `adhoc`. |
| `merlin_prompt` | No | Free-text prompt, used when `query_type` is `merlin`. |
| `callback_url` | No | Webhook URL to notify on completion. |

**Example prompt:** _"How many users opened an email in the last 7 days but didn't purchase? Don't create a segment, just give me the count."_

<Note>
  The same "internal names only" rule applies: resolve event and attribute names with the discovery tools before creating a query, and validate the filters with `deep_validate_segment_filters` first. The same negation rule applies as well: express "did not do the event" with a positive filter in `excluded_filters` or with `"execution": {"type": "atmost", "count": 0}`, never with `executed: false`.
</Note>

Reachability counts for a recent query are currently computed with a standard server-side configuration.

<Note>
  Every query created through this tool computes reachability for all four channels (push, email, SMS, and WhatsApp), with push counts broken down by platform (Android, iOS, and web). Per-channel configuration in the `reachability` parameter is part of the API request format but is not applied to queries created through this tool today, so omitting the parameter gives the same result as passing it.
</Note>

Identical queries are also deduplicated for a short window.

<Note>
  Submitting a `create_recent_query` request with the same filters and options as an earlier request within the last 15 minutes returns the same `rq_id` as that earlier run instead of starting a new query. To get a genuinely fresh count for the same audience, wait for the window to pass.
</Note>

### `get_recent_query`

Fetches a recent query by its `rq_id`, including its `status` and, once the query succeeds, the `user_count` and reachability counts. Poll it after `create_recent_query` until `status` is `success` or `failure` (see `failure_reason`). While the query is in progress, `status` is `received`, `running`, or `retry_wait` (a transient failure being retried automatically).

| Parameter | Required | Description |
| --- | --- | --- |
| `rq_id` | Yes | The query's 24-character ID returned by `create_recent_query`. |

### `get_recent_query_filters`

Returns only the filter definition (included/excluded filters, platforms, and the reachability request) that a recent query was created with. Use it to inspect an earlier query's audience, or to clone it into a new query or a saved segment.

| Parameter | Required | Description |
| --- | --- | --- |
| `rq_id` | Yes | The query's 24-character ID. |

## Check Segment Membership in Real Time

Use this tool for an immediate, single-user answer rather than a full audience count.

### `is_user_in_segment`

Checks in **real time** whether a specific user is a member of one or more segments, up to **10 segments per call**. Results are returned in the same order as the requested segment IDs.

| Parameter | Required | Description |
| --- | --- | --- |
| `uid` | Yes | The customer's own user identifier (the `uid` field in user profiles), **not** the internal MoEngage ID. |
| `segment_ids` | Yes | List of 1–10 segment IDs to evaluate. |

Each result carries a `segment_eligibility` flag:

- `true`: the segment can be evaluated in real time; `user_in_segment` (true/false) is present and authoritative.
- `false`: the segment **cannot** be evaluated in real time (file-based, funnel, retention, and predictive segments are batch-only); `user_in_segment` is absent and a `message` explains why.

<Warning>
  `segment_eligibility: false` means "could not evaluate in real time"; it is **not** a "no". Always check `segment_eligibility` before acting on `user_in_segment`.
</Warning>

A few other request details apply:

<Note>
  Duplicate segment IDs are de-duplicated server-side before the 10-segment limit is applied. A `404` (Not Found) means no user was found for the given `uid` in this workspace.
</Note>

**Example prompt:** _"Is user `alice@example.com` in my 'Cart abandoners' and 'VIP customers' segments right now?"_

## Limits

The segmentation tools do not enforce rate limits of their own; the limits below come from the MoEngage APIs they call. There is no published quota on how many segments or queries you can create in a period, no enforced minimum interval between polls, and no documented cap on concurrent count jobs.

| Limit | Value |
| --- | --- |
| Segments evaluated per `is_user_in_segment` call | 10 |
| Values returned by `get_value_suggestions` | 5,000 distinct values |
| Segments returned per `list_segments` page | 1 to 100 (default 10) |
| Segment count result cache | 15 minutes |
| `create_recent_query` deduplication window | 15 minutes (an identical request returns the same `rq_id`) |
| Filter payload size | Oversized or overly deep filters are rejected with a `413` (Payload Too Large) error |
| Filter nesting depth | One level of `nested_filters` |

Rate limiting can still occur at the platform level.

<Note>
  Some segmentation APIs, including the real-time membership check, can return a `429` (Too Many Requests) error under heavy traffic. There is no published request quota; when a `429` occurs, retry after about 60 seconds. All tool calls also pass through the MoEngage API gateway, which can apply its own traffic controls.
</Note>

## Known Behaviors and Limitations

This section lists known constraints so you and your assistant can plan around them.

- **Internal names only.** Filters usually accept display names at create time. `create_custom_segment` has a partial safety-net catalog check, but it fails open when the catalog is unavailable, so an unresolved bad name can still surface later as a count job that fails with no error reason. Always resolve names via `find_events` / `find_user_attributes` / `find_event_attributes` first, and validate with `deep_validate_segment_filters`.
- **Stale events are hidden.** `find_events` excludes events inactive for more than 60 days.
- **Text equality uses the `is` operator.** The operator `equals` on a `user_attributes` filter is rejected with a generic `400` (Bad Request) error.
- **Negative event conditions require a specific pattern.** `executed: false` on an `actions` filter is silently ignored. Express "did not do the event" with a positive filter in `excluded_filters`, or with `"execution": {"type": "atmost", "count": 0}`.
- **Identical recent queries are deduplicated.** An identical `create_recent_query` request within 15 minutes returns the same `rq_id` instead of running a new query.
- **Segment types vary in MCP support.** `create_custom_segment` only creates filter-based (ELASTIC_SEARCH) segments. `list_segments` returns Filter and File segments, but excludes Warehouse, Analytics, and Composite. `get_segment` returns a full filter tree only for Filter segments; File and cohort-import segments return metadata only. `is_user_in_segment` evaluates Filter segments in real time; file-based, funnel, retention, and predictive segments are batch-only. See [Types of Segments](/user-guide/segment/basics-of-segmentation/types-of-segments) for what each type means.
- **Counts are cached for 15 minutes.** `start_segment_count` returns the cached result (`served_from_cache: true`) when a successful count already exists within the window.
- **Validation returns HTTP 200 either way.** For `deep_validate_segment_filters`, check `is_valid` in the response body.
- **Value suggestions are capped** at 5,000 distinct values per attribute.
- **Role-based permissions apply.** Creating segments and queries requires the matching create/manage permission on your MoEngage role; read tools require read access. See [Security and Permissions](/user-guide/ai-and-intelligence/merlin-ai/moengage-mcp-server#security-and-permissions).

## Troubleshooting

<AccordionGroup>
  <Accordion title="A segment count fails with no error reason">
    This almost always means a filter uses a display name instead of an internal name. Resolve names with the [discovery tools](#discover-events-attributes-and-values) and re-validate with `deep_validate_segment_filters` before creating the segment again.
  </Accordion>

  <Accordion title="A segment or query is not created">
    Check the response for a specific error code: `409` means the name is already taken, `400` means the filter structure is malformed, and `413` means the filter is too large or deeply nested. A `400` on a filter that otherwise looks right is often the operator: use `is`, not `equals`, for text equality. See the common-errors note under [Create and Browse Segments](#create-and-browse-segments).
  </Accordion>

  <Accordion title="is_user_in_segment returned segment_eligibility: false">
    This is not a "no": it means the segment type does not support real-time evaluation (file-based, funnel, retention, and predictive segments are batch-only). Check the segment's type, or fall back to a saved count with `start_segment_count`.
  </Accordion>

  <Accordion title="A segmentation tool isn't available to the assistant">
    Tool availability depends on your MoEngage role and your client's connector settings. See [Security and Permissions](/user-guide/ai-and-intelligence/merlin-ai/moengage-mcp-server#security-and-permissions) and [Enable the Tools You Need](/user-guide/ai-and-intelligence/merlin-ai/moengage-mcp-server#enable-the-tools-you-need) on the MCP Server and Connector page.
  </Accordion>
</AccordionGroup>

## Example Prompts

| What you want to do | Example prompt |
| --- | --- |
| Explore the catalog | _"What purchase-related events do we track, and what attributes do they have?"_ |
| Sanity-check a filter | _"Before creating it, explain in plain English what this segment's filters mean."_ |
| Create a segment | _"Create a segment of users in Mumbai who purchased at least 3 times in the last 30 days."_ |
| Count a segment | _"How many reachable users are in my 'Cart abandoners' segment, split by channel?"_ |
| Count without creating | _"How many users opened an email in the last 7 days but didn't purchase? Just the count, don't create a segment."_ |
| Check membership | _"Is user 12345 currently in the 'Churn risk' segment?"_ |
