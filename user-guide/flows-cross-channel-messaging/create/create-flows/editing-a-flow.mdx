# Overview

Optimizing a flow is often an iterative process. To iteratively improve your flow, you must edit your published flows. You can experiment with a new channel or a new strategy altogether to improve flow performance. Versioning of flows enables you to achieve the same for any published flow without creating multiple separate flows. It allows you to keep all the analytics and context of the flows intact.

Versioning helps you edit published flows while efficiently managing them and viewing the revision history using logs rather than creating duplicate independent flows. You can add, remove, and change elements, add stages and parameters, and change flow paths and configurations in published flows.

This improves operational efficiencies when experimenting and optimizing customer journeys while reducing confusion and clutter. Versioning also provides you with clear reporting and insights on the performance of each version of your flow.

## Use Cases

- A retail brand runs a monthly discount campaign in the last week of each month. They communicate this through a multi-channel approach using a series of carefully crafted emails, SMS, and Push notifications. But the performance of these campaigns has dropped in the last few months. They can edit their flow to create improved versions of the running campaigns and optimize these campaigns.
- A retail brand can edit its flows and create multiple versions to test different user paths messaging, and creative elements in a published flow without having to duplicate the entire flow. They can create multiple versions of the same flow with different channels, conditions, and stages to evaluate whether this drives improved engagement and conversions.
- By editing a flow and iteratively creating flow versions, a fintech app can make changes to its published flows based on feedback from its customers. For example, if customers are having trouble navigating through the app, the fintech app can use versioning to quickly make changes to the flow and improve the user experience.

## How does versioning work?

When a published flow is edited, a new version is created. For example, on adding or deleting a stage or changing the Flows settings (like conversion tracking and control group), a new version of the flow is created regardless of whether the changes are saved.

When you are done with all the changes, you can publish the newly created version. When published, the new users that satisfy the entry condition will enter the latest published version.

For users who are already active in the previous version, you decide what happens at the time you publish. You can either let them finish the version they are in, or move them into the new version. For more information, refer to [Publishing a new version](/user-guide/flows-cross-channel-messaging/create/create-flows/editing-a-flow#publishing-a-new-version).

When a new version is created for the Flow, the following happens:

- The versions are typically named 'Version 'n'' depending on the number of versions spanned for the Flow. In the case of our example, the active Flow is labeled as 'Version 1', and the version being edited is termed as 'Version 2'.
- A version selector(dropdown) is added next to the flow name to help you track the versions. The version being edited is selected in the dropdown. The version selector has the following information: <img src="/images/moengage_039a13.png" alt="Version_Dropdown.png" />
- You can view the changes by clicking on the "View Changes" hyperlink at the top ribbon (Flow details section) of the page above the Flows canvas. This hyperlink will open the version logs, where you can see the unsaved and saved changes. For more information, refer to Version Logs. <img src="/images/moengage_d8225c.png" alt="View_Changes.png" />
- Once you've made the desired changes, click _Save_ on the top ribbon of the page above the Flows canvas. The changes saved will be available in the \_Saved\_section of the Version Logs.
- Upon saving a version, you'll get the following option on the top of the page above the Flows canvas:
  | Action | Description |
  | --- | --- |
  | View changes | Lets you view the version logs. |
  | Delete | It lets you delete the saved version. Once deleted, the version cannot be recovered. |
  | Publish | Lets you publish the draft version. MoEngage [retires](/user-guide/flows-cross-channel-messaging/create/create-flows/status-of-flows#retiring-a-flow) the currently active version only when the version you publish becomes active. If you schedule the new version, the current version stays active until the scheduled time.  <br />**Note:** If the previous version is in [paused status](/user-guide/flows-cross-channel-messaging/create/create-flows/status-of-flows#pause%2Fresume), publishing the draft version will stop the previous version. |
  | Save | Allows you to save the changes to the current version of the Flow. |
  | Duplicate | It lets you duplicate the current version of the Flow.  <br />**Note**: A duplicate flow of the current version will be created. However, the duplicated Flow will not contain all the versions of the Flow being duplicated. The duplicate Flow will only have the information contained in the current flow version being duplicated. |

### How does limiting user entry work across Versions?

The user entry limits are defined at the version level. So everytime a new version is published, the limit defined is refreshed for the users.\
For example:

- If the Limit was defined to be 1 in Version 1 and was changed to 2 in Version 2:
  - Irrespective of whether user entered in Version 1 once or not, All users at max will be able to enter Version 2 twice, as the Limit of Version 2 is 2.

## When is a new version created?

The following actions will lead to the creation of a new version:

| Flow Element/Settings | Actions that will lead to the creation of a new version |
| --- | --- |
| Audience | <ul><li>Changing the Flow's audience</li></ul> |
| User Entry Conditions and Limits | <ul><li>Changing the Trigger condition and Delay associated with it</li><li>Changing the User Entry Limit</li></ul> |
| Conversion Goals | <ul><li>Adding, deleting, or editing the Conversion Goals added for the Flow</li><li>Editing the Attribution Window added for the Conversion Goals</li><li>Enabling/disabling the Exit on conversion toggle for the Flow</li></ul> |
| Other Flow Settings | <ul><li>Changing control group settings</li></ul> |
| Action Stage | <ul><li>Adding or deleting a stage</li><li>Adding or deleting a variation/locale</li><li>Changing the User Distribution settings</li><li>Changing the fallback channel/Default time settings, adding or deleting NBA channels, enabling or disabling BTS</li></ul> |
| Conditions (Check User Attribute/ Has done event/Conditional split) | <ul><li>Changing the condition of the stage or the branch</li><li>Changing the evaluation window</li><li>Adding or deleting a branch</li><li>Changing the order of branches</li></ul> |
| Controls (Wait for/till, Goto, Intelligent Path Optimizer (IPO), A/B Split) | <ul><li>Changing the settings of Wait Till/For stage</li><li>Changing the Goto Destination</li><li>Switching A/B split to IPO</li><li>Changing the User distribution between AB Split branches</li><li>Adding or deleting a branch of AB split/IPO</li><li>Changing the Metric maximized by Merlin AI</li></ul> |

<Info>
      - Versioning is not applicable for the following flow statuses: Stopped, Retired, Completed, and Draft, and also for the 'One-time' time-based Entry flows. To bring back an earlier version of an active flow, refer to [Restoring a previous version](/user-guide/flows-cross-channel-messaging/create/create-flows/editing-a-flow#restoring-a-previous-version).
      - The Entry Type cannot be changed for a published Flow.
      - Changing the control group settings or the User Entry Limit condition in a Scheduled Flow will not create a new version.
      - For active and paused flows, the Flow's schedule settings cannot be edited except for the 'End Date' for periodic times.
      - Changes to flow name, flow status, DND, and FC settings, and changes in the content of existing action campaigns, do not lead to creating new versions of the Flow.
</Info>

## Publishing a new version

When you publish a new version, MoEngage asks what should happen to the users who are still active in the previous version.

<Info>
  Creating a version requires Create access in the Campaigns module. Publishing it, and with it choosing what happens to the active users, requires Publish access. Anyone with View access can see the version's stats.
</Info>

To publish a new version, perform the following steps:

1. On the flow canvas, click **Actions**, and then click **Publish**.
2. In the **Publish new version** dialog box, select one of the following options:

   | Option | What happens |
   | --- | --- |
   | Let them continue on the previous version | Active users finish the version they are in. MoEngage marks that version **Completed** once all of them exit. |
   | Move them to this version as soon as possible | MoEngage transitions active users into the new version. Users who cannot be mapped to a stage exit the flow. |

3. Click **Publish**.

There is no default selection, so you must choose one of the two options before you can publish. The choice applies only when the new version becomes active, not at the moment you publish it.

<Note>
  The choice affects only the version published immediately before this one. If you publish Version 3, it applies to the active trips in Version 2 and not to any earlier version.
</Note>

If you schedule the version, the dialog box states the date and time it goes live, and the current version stays active until then. The dialog box also lists the resulting status of each version, so you can confirm which version retires and which becomes active before you publish.

### How users move between versions

When you choose to move active users, where each user lands depends on the change you made. Users at a wait stage, at a condition stage with **Keep Evaluating For** turned on, or at an action stage where DND is not ignored move only after their pending delay ends.

| Change you made | Where active users go |
| --- | --- |
| Added a stage | Users who have not yet reached the new stage pass through it. Users who are already past that point continue downwards in the new version. |
| Deleted a stage | Users at or just above the deleted stage move to the new child of the stage they are in. Users past that point continue downwards. |
| Deleted a branch | Users evaluated into a branch that still exists continue. Users evaluated into the deleted branch, or already inside it, drop off. |
| Updated a stage's configuration | Users already in the edited stage are evaluated against the configuration that applied when they entered. Everyone else uses the new configuration. |

MoEngage raises the **User Exited Flow** event for each user who leaves the previous version, with one of the following exit reasons:

- **Move to new version**, when the user enters the new version.
- **Dropped off as the path was no longer defined**, when no matching stage exists for the user in the new version.

Drop-offs are attributed to the version the user left. You can find these users in Behavior Analytics by querying the **User Exited Flow** event with the exit reason, constrained on the flow ID.

### Sending a new version for approval

If your workspace uses the campaign approval workflow, **Actions** shows **Send for approval** instead of **Publish**, and the dialog box has two steps:

1. Under **Manage users from previous version**, select what happens to the active users, and then click **Next**.
2. Select your approvers, add a comment if needed, and then click **Send for approval**.

MoEngage asks for the choice every time the version goes for review, including when you edit a version that is already under review or resubmit one that was rejected.

### Viewing the choice later

Flow Settings shows the option that was selected when the version was published. The value is read only, so you cannot change it after publishing, and it appears only on flows that have two or more versions. Approvers can use it to see the decision before approving a version.

## Restoring a previous version

If a newer version is not performing as expected, you can bring back an earlier version instead of rebuilding it. Restoring copies that version into a new draft, which you can then edit and publish like any other version.

To restore a previous version, perform the following steps:

1. In the version selector next to the flow name, select the version you want to restore.
2. Click **Actions**, and then click **Restore as draft**.
3. In the confirmation dialog box, click **Restore as draft**.

MoEngage creates a copy of the selected version as the next version number in **Draft** status. The restored draft is not active until you publish it.

<Info>
  - **Restore as draft** requires Create access in the Campaigns module.
  - The option is available while the latest version is active, scheduled, or paused.
  - The option is not available when the latest version is stopped.
  - If the latest version is retired, the option appears only when editing a retired flow is enabled for your workspace.
</Info>

## Stopping a flow that has active older versions

Stopping the latest version does not stop the earlier versions on its own, so users still active in those versions continue to receive messages. When you stop the latest version, MoEngage checks the earlier versions for active trips and lets you stop them at the same time.

To stop the older versions along with the latest one, perform the following steps:

1. Click **Actions**, and then click **Stop**.
2. In the confirmation dialog box, select the **Also stop previous version(s) with active trips** check box.
3. In the **Select more version(s) to stop** list, select the versions to stop.
4. Confirm the action.

Stopping a flow is irreversible. Once stopped, you cannot edit or resume the flow, though you can still duplicate it. Any active trips in the versions you stop remain at their current stage and do not advance.

<Note>
  MoEngage does not ask this when a version moves from retired to stopped on its own, because all the active users of the latest version have already exited.
</Note>

## Switching between versions

When you switch between versions, the following happens:

      - If the current version is not saved, you will be asked if you want to save the changes. If you choose not to save, the version will not be retained, and all the changes will be discarded.
      - When you switch versions after saving (but the saved version is not published), you'll be notified of the same with the following alert beside the version selector. <img src="/images/moengage_5f4070.png" alt="Save_Options.png" />

## Logs

With the possibility of editing a published flow comes the question What are the changes made, Who made the changes, and when. The following logs will help marketers answer the above questions both for a Version and across multiple versions of a flow:

### Version Logs

Version logs are available for the versions of the Flow in the draft state and answer the above three questions to a version. You can access the version logs by clicking the \_View Changes\_label at the top ribbon (Flow details section) of the page above the Flows canvas. The following details are available in the version logs:

    - **Unsaved** - Details and Dates are available in this section. You can see the details of the changes made to the version listed. Click on the change listed, and you will be shown the node/stage where the change was made, as illustrated in the image below.
    - **Saved**- User, Details, and Date are available in this section, as shown below. Also, you can see the details of the changes made to the version.

![VersionLogs.gif](/images/moengage_d9156b.png)

### Audit Logs

Audit logs are available for all versions of the Flow. They contain the following information for each version:

    - **Version** - This field indicates the version name of the Flow.
    - **Status** - This field indicates the status of the version.
    - **Details** - This field contains information about whether the version was published and the list of changes made, has saved changes with a list of changes made, and so on.
    - **User** - This field contains information about who made the most recent edit to the version of the Flow.
    - **Date** - This field contains information about when the most recent edit to the version happened.

![AuditLogs.gif](/images/moengage_b15615.png)

## Finding users who entered a Flow Version

Once you create a new version, you might want to find users who have entered the new version and compare their performance with respect to an older version of the same flow.

You can create a segment with all the users who have performed the _User entered flow_ event with the _Flow Id Attribute_ value being the [flow-id](/user-guide/flows-cross-channel-messaging/analyze-flows/tracking-users-in-flows) of your flow, with the _Flow Version Name_ attribute as the particular version name (For more information, refer to [finding the version name for a Flow](/user-guide/flows-cross-channel-messaging/create/create-flows/editing-a-flow).
