The filter builder lets you build audiences from data in your warehouse using the same dropdown filters you use for regular MoEngage segments. You pick attributes and events from a list rather than writing a SQL query, so you do not need to involve your analytics team to create or change a segment.

MoEngage builds the SQL for you and runs it against your warehouse. Your data stays where it is.

<Info>
  **Prerequisites**

  - A data warehouse connection set up in App Marketplace. For more information, refer to [Connect Your Data Warehouse](/user-guide/segment/create-segments/warehouse-segments/connect-your-warehouse).
  - Your warehouse tables mapped to MoEngage users, events, and attributes. Your data or engineering team does this once in [Map Your Warehouse Schema](/user-guide/segment/create-segments/warehouse-segments/map-your-schema). Only mapped columns appear in the dropdowns.
</Info>

<Note>
  The filter builder supports **BigQuery** and **Databricks**. Support for Snowflake and Redshift is planned for a later release.

  This is one of two ways to build a warehouse segment. For a comparison with the SQL method, refer to [Warehouse Segments](/user-guide/segment/create-segments/warehouse-segments).
</Note>

# Build a Segment

<Steps>
  <Step title="Select your source">
    On the Create Segments page, choose your warehouse connection from the **Source** dropdown. Selecting an external source loads the attributes and events mapped from that connection.
  </Step>
  <Step title="Add your filters">
    Use the **User Property** and **User Behaviour** sections to define your audience. Combine filters with AND, OR, and Exclude conditions, and nest them as needed.
  </Step>
  <Step title="Check the count">
    Click **Show count**. MoEngage runs the query against your warehouse and matches the returned users against users in MoEngage, then reports rows fetched, user count, and reachable count.
  </Step>
  <Step title="Save the segment">
    Give the segment a name and description and save it. Saved segments appear on the All Segments page with the type **Filter - external**.
  </Step>
</Steps>

<Warning>
  Queries run on your data warehouse directly, so you incur the compute costs your warehouse charges for them.
</Warning>

## Filter on User Properties

The **User Property** section shows a single dropdown listing every user attribute available to you:

- Attributes from your user master table.
- Attributes from lookup trait tables joined to users.
- Attributes from lookup trait tables joined to those lookup trait tables.

All attributes appear upfront regardless of which table they come from. You do not pick a table first.

**Example.** A fashion retailer maps a Membership Plan table to users and a Plan Perks table to Membership Plan. Plan Perks has no direct link to users — it reaches them through Membership Plan. To target users whose plan includes an unexpired free shipping perk, you select `perk_type is Free Shipping`, add an AND condition, and select `expiry_date is after today`. Both attributes come from Plan Perks; MoEngage resolves the two-hop join for you.

Once lookup trait tables are mapped, user attributes are grouped by their source table in the dropdown. Event attributes are not grouped.

## Filter on User Behaviour

The **User Behaviour** section uses the same **Has Executed** and **Has Not Executed** pattern as regular segments. Warehouse events appear alongside your other events.

After selecting an event, add a **With Attribute** filter to see every attribute available for that event — event attributes from the event table, plus attributes from lookup trait tables joined to that event, up to two hops away.

How a filter evaluates depends on the relationship type your team configured:

| Relationship | How the filter evaluates |
| --- | --- |
| **1:Many** | Matches if any related row satisfies the filter. Selecting `product_category is Footwear` on an Order Placed event qualifies the order if any product in it is footwear. |
| **Many:1** and **1:1** | Evaluates the single related row directly, with no any-match behavior. |

### Event Occurrence Operators

Set how many times a user performed the event:

| Operator | What it matches |
| --- | --- |
| **exactly** | The user performed the event exactly n times. |
| **at least** | The user performed the event n or more times. |
| **at most** | The user performed the event n or fewer times. |
| **for the first time** | The user's first occurrence of the event falls inside the date range, with no occurrence before it. |
| **for the last time** | The user's most recent occurrence of the event falls inside the date range. |

<Note>
  **for the first time** and **for the last time** are bounded by the query window set on your warehouse connection — 60 days by default. An event that first occurred before that window looks like a first occurrence inside it.
</Note>

## Operators by Data Type

Available operators depend on the MoEngage data type your team mapped the column to.

| Data type | Operators |
| --- | --- |
| **String** | is, is not, contains, contains spaces, does not contain, starts with, does not start with, ends with, does not end with, exists, does not exist, is empty, is not empty |
| **Boolean** | is, is not, exists, does not exist |
| **Numeric** | is equal to, is not equal to, is between, is not between, is less than, is greater than, exists, does not exist |
| **Array (numeric)** | (any of / all of) is equal to, is not equal to, (any of / all of) is between, is not between, (any of / all of) is less than, (any of / all of) is greater than, exists, does not exist |
| **Array (string)** | (any of / all of) is, is not, (any of / all of) contains, (any of / all of) contains spaces, does not contain, (any of / all of) starts with, does not start with, (any of / all of) ends with, does not end with, exists, does not exist, (any of / all of) is empty, is not empty |
| **Date / time** | on, is between, before, after, in the next, in the last, is today, exists, does not exist |
| **Time of the day** | is, is between, in the following |
| **Day of the week** | is, is between, in the next, in the last, is today, in the following |
| **Day of the month** | is, is between, in the next, in the last, is today, in the following |
| **Month of the year** | is, is between, in the next, in the last, is this month, in the following |

You can also compare one attribute against another, and use special date filters, as you can in rule-based segments. For more information, refer to [Filters in Segmentation](/user-guide/segment/advanced-concepts/filters-in-segmentation).

# What You Can Do With the Segment

Once saved, a segment built this way behaves like any other custom segment on the All Segments page. You can view it, edit it, duplicate it, archive it, and create a campaign from it.

The segment detail page shows its type, source connection, creation date, last run time, user count, reachability, and edit history. Running the segment from this page refreshes the user count by re-querying your warehouse. Segments used in a campaign refresh automatically at campaign run time.

The **Recent Query** view lists your recent segment runs. Unlike the SQL editor, it does not report runtime, data scanned, or rows fetched.

To export the users in a segment, use the standard segment export, which exports MoEngage attributes. MoEngage cannot resolve warehouse attribute values during export, so warehouse columns are not included.

# Not Supported

The filter builder does not support:

- **Aggregation operations** on warehouse data, including change and percentage-change aggregations. Use the [SQL editor](/user-guide/segment/create-segments/warehouse-segments/create-using-sql) instead.
- **All Users segments.** Every warehouse segment needs at least one filter.
- **Waterfall analysis.**
- **Value suggestions.** Attribute value dropdowns stay empty — type values manually.
- **Analyse.** Warehouse segments cannot be used as the audience for an analysis.
- **Affinity segments and custom segments** as filters inside a warehouse segment.
- **Object and object array attributes**, and boolean or date arrays.

# When a Segment Breaks

If your warehouse schema changes in a way that breaks a segment — a renamed column, a dropped table, a changed data type — MoEngage marks the segment **Broken**, sends an email alert, and shows a banner on the segment detail page.

Broken segments appear under an **Action Required** view on the All Segments page. Your data team fixes the underlying mapping in [Map Your Warehouse Schema](/user-guide/segment/create-segments/warehouse-segments/map-your-schema), after which you can re-run the segment.

# Considerations

- A segment reads from one warehouse connection. To combine data across connections, save a segment per connection and combine them as custom segments.
- Only users who already exist in MoEngage are matched. Users present in your warehouse but not in MoEngage are skipped — mapping a schema does not import users.
- Event filters read only as far back as the query window set on the connection, 60 days by default.
- Attribute value dropdowns show up to 1,000 distinct values.
