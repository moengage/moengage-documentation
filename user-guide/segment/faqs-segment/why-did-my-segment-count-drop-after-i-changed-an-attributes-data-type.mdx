## Problem

An event or user attribute had its [allowed data type](/user-guide/settings/data-management/overview-data-management#set-allowed-data-types) changed — commonly from String to Date — and afterwards:

- A segment or analysis that filters on the attribute returns 0 users, or a count far below the number of users the attribute is set on.
- The segmentation dropdown lists the attribute under both the old and the new data type.
- Value suggestions still show values in the old format.

The data itself is present. Ingestion is not failing, and the values appear on user profiles and in the attribute's tracked data.

## Instructions

Changing an allowed data type applies to data ingested after the change. MoEngage does not convert values already stored under the previous data type and does not rewrite past events, so the attribute holds a mix of both data types.

A query evaluates the attribute as one data type at a time. Filtering as the new data type therefore matches only the values ingested since the change, which is why the count is low rather than zero-by-error. The count grows as new data arrives.

Confirm this is what you are seeing before changing anything else:

1. Open **Settings** > **Data Management** and find the attribute. Check that the allowed data type is the one you expect, and note when it was changed.
2. In the segmentation query builder, select the attribute and check whether more than one data type is offered. Both types being listed confirms the attribute holds historical values under the old type.
3. Run the query once against each data type separately and compare the counts. The old type returns the historical users; the new type returns those ingested since the change.

To reach the full audience while both data types are present, choose one of the following:

- **Query both data types with OR.** Add one condition per data type and combine them with the OR operator — the attribute as Date for newer values, OR the attribute as String for older values.
- **Re-ingest the historical values in the allowed data type.** This is the option to choose when you need relative date operators, or when the segment will be reused across many campaigns and a two-condition query is hard to maintain.
- **Wait, where the segment only needs recent data.** If the query covers a recent window that falls entirely after the data type change, filtering on the new data type alone is correct and no workaround is needed.

<Warning>
  Relative date operators, such as "in the last 7 days", are available only on the Date data type. Values still stored as String cannot be filtered by a relative date, so a query spanning both data types needs an absolute value or range for the String condition. Where the full history has to be matched with relative dates, re-ingest the historical values instead.
</Warning>

Value suggestions behave the same way: they are generated from data already ingested, so suggestions in the old format continue to appear until those values fall outside the [value suggestions](/user-guide/segment/advanced-concepts/value-suggestions) retention window. Suggestions for both data types are expected and do not mean the change failed to apply.

## Example

A user attribute holding a subscription expiry date was ingested as String for a year, then set to an allowed data type of Date so that relative date operators could be used. A segment filtering the attribute as Date returns a handful of users, although the attribute is set on nearly the entire user base.

Running the query against the String data type returns the historical users, which confirms the values are present and only their stored data type differs. Combining both conditions with OR — the attribute as Date, OR the attribute as String — returns the full audience. Because the campaign needs a rolling window rather than a fixed date, the historical values are re-ingested as Date so that relative date operators apply to the whole history.
