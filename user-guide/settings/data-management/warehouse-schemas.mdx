A warehouse schema maps one table or view in your data warehouse to MoEngage users, events, or attributes. Once you map your tables, the columns become available as dropdown options in the segment builder, so your marketers can build warehouse segments without writing SQL.

You set up warehouse schemas once. Your marketers then use the result to build audiences — refer to [Create a Warehouse Segment Using Filters](/user-guide/segment/create-segments/warehouse-segments/create-using-filters).

<Info>
  **Prerequisites**

  - A connected data warehouse. The connection steps and the read permissions MoEngage needs differ by warehouse — refer to [Connect Your Data Warehouse](/user-guide/segment/create-segments/warehouse-segments/connect-your-warehouse).
  - Admin access, or a custom role with warehouse schema permissions.
</Info>

<Note>
  Warehouse schemas support **BigQuery** and **Databricks**. Support for Snowflake and Redshift is planned for a later release.
</Note>

# How Warehouse Schemas Work

MoEngage does not copy your warehouse data. It reads your schema definitions, builds a SQL query from the filters selected in the segment builder, and runs that query against your warehouse when a segment is evaluated.

Each schema is a 1:1 mapping to a single table or view. You map three types of tables:

| Table type | What it holds | How many |
| --- | --- | --- |
| **User master** | The full set of unique users, keyed by a user identifier column. Other columns become user attributes. | One per connection |
| **Event** | Behavioral data, with one row per event occurrence. Has a many-to-one relationship with users. | Many |
| **Lookup traits** | Relational or lookup data — products, stores, subscription plans — that enriches users or events. | Many |

<Note>
  Lookup traits are referred to as data entities in some MoEngage interfaces and API responses.
</Note>

## Mapping Order

The mapping order is enforced in the dashboard. Options for a table type stay disabled until the tables they depend on are mapped.

<Steps>
  <Step title="Map the user master table">
    Required first. Every other table needs a path back to the user master table.
  </Step>
  <Step title="Map event tables">
    Available after the user master table is mapped.
  </Step>
  <Step title="Map lookup trait tables">
    Available after the table they relate to — a user, event, or another lookup trait table — is mapped.
  </Step>
</Steps>

# Connection-Level Settings

Two settings apply to every schema created under a connection. Both are set on the connection itself, not on individual schemas.

| Setting | Required | Description |
| --- | --- | --- |
| **Query window** | Yes | How far back MoEngage reads event data. Choose 30, 60, 90, 180, or 360 days. Defaults to 60 days. This applies only to event tables — user master and lookup trait tables are not time-bound. |
| **Date/datetime format** | Yes | The format your warehouse stores timestamps in. No default — you must select one. |

<Warning>

</Warning>

# Create a Schema

To create a schema, go to **Settings** > **Analytics and Data** > **Warehouse Schemas** and click **+ Schema**.

{/* TODO: Confirm the exact Settings navigation path against the dashboard. Other pages document Data Management under Settings > Data. */}

The listing page has three tabs — **Events**, **User attributes**, and **Lookup traits** — showing the schema name, source connection, table name, created date, and creator. From each row you can view details, edit, duplicate, or delete a schema.

## Map the User Master Table

The user master table defines the universe of users MoEngage can segment. Each connection has exactly one.

<Steps>
  <Step title="Select the source">
    Choose the connection, then the database and table. The database and table dropdowns populate from the connection.
  </Step>
  <Step title="Preview the data">
    Click **Preview** to see the top 5 rows from the table before mapping columns. Select or search for the columns you want to see — warehouse tables can carry thousands of columns, so previewing them all at once is not practical.
  </Step>
  <Step title="Map the user identifier">
    Map the column that holds your user ID. MoEngage matches this against the customer ID on existing MoEngage users.

    Exactly one column can serve as the user identifier. Composite identifiers made of two or more columns are not supported.
  </Step>
  <Step title="Map the remaining columns">
    Map each remaining column to a MoEngage user attribute, or mark it as skipped. Skipped columns are not read and do not appear in the segment builder. You can skip columns individually or skip all of them at once.

    Each mapped attribute takes a display name, which is what appears in the segment builder instead of the raw column name, and an optional description.

    To map a large table without working through it column by column, use **Upload mapping file** and supply the mapping as a JSON file.
  </Step>
  <Step title="Save">
    MoEngage runs a validation query against your warehouse to confirm the user identifier column is non-null and unique.
  </Step>
</Steps>

<Warning>
  Users whose identifier is null, empty, or absent from MoEngage are skipped. Warehouse segments target users who already exist in MoEngage — mapping a schema does not create new users.
</Warning>

Each column shows both its warehouse data type and the MoEngage data type it maps to. A Redshift `VARCHAR`, for example, maps to a MoEngage String. Check these pairs before saving to avoid type mismatches in the segment builder.

## Map an Event Table

Event tables hold behavioral data. The user identifier and event time columns are both mandatory; every other column is optional and becomes an event attribute.

<Note>
  A table can be used in one mapping only. Once you map a table as an event, it cannot also be mapped as a user master table, a lookup traits table, or a second event.
</Note>

Your warehouse stores events in one of two patterns:

<Tabs>
  <Tab title="One table per event">
    Every row in the table is the same event. Enter a name for the event — this is the name that appears in the segment builder.
  </Tab>
  {/* TODO: Mapping several events from a single table is not expected to be part of the first release. Confirm before publishing, and cut this tab if it did not ship. */}
  <Tab title="One table for all events">
    The table holds several event types, distinguished by an event name column. Map that column, then select which event to import. MoEngage filters rows to the selected event, including in the preview.

    Only string columns can be selected as the event name column. MoEngage shows 10 sample values from the column before fetching the full list of distinct event names.

    <Note>
      If fetching distinct event names runs longer than 15 minutes, MoEngage stops and asks you to confirm the column selection. A long-running query usually means the column has high cardinality and is not an event name column.
    </Note>
  </Tab>
</Tabs>

Only date and datetime columns can be selected as the event time column. MoEngage reads event times as UTC and converts them to your workspace timezone for display.

If your event table is partitioned, map the **partition identifier** column as well. This is optional, and lets MoEngage restrict queries to the relevant partitions instead of scanning the whole table.

## Map a Lookup Traits Table

Lookup trait tables carry relational data that enriches users or events — a Products table joined to an Order Placed event, or a Membership Plan table joined to users.

### Join Rules

Every lookup trait table needs a join path back to the user master table. MoEngage blocks chains that do not resolve to a user.

Valid paths:

```text
Lookup trait → User
Lookup trait → Event → User
Lookup trait → Lookup trait → User
Lookup trait → Lookup trait → Event → User
```

You can join on any column in either table. Select the relationship type that matches your data:

| Relationship | Meaning |
| --- | --- |
| **1:1** | One user or event row maps to one lookup trait row. |
| **1:Many** | One user or event row maps to many lookup trait rows. |
| **Many:1** | Many user or event rows map to one lookup trait row. |

### Test the Join

Run **Test join** before publishing. MoEngage runs the join against your warehouse and returns the top 5 rows of the joined result so you can confirm the keys are correct.

<Warning>
  If the join returns no rows, you cannot publish the schema. A join that matches nothing usually means the wrong column was picked on one side, and publishing it would produce segments that silently return no users.
</Warning>

### Join Depth Limits

A join path can be six levels deep, counting the user master table as the first level. That leaves five tables chained after it. The limit exists because every level adds a join to the generated query, and warehouses cap how large a query can get. It is configurable — to raise it, contact [MoEngage Support](https://help.moengage.com/hc/en-us/requests/new).

MoEngage validates join depth when you save a schema, not when a segment runs, so you find out immediately rather than when someone builds a query.

# Keep Schemas in Sync

MoEngage reads your warehouse metadata — databases, tables, and columns — on a schedule rather than live. Exploring a large warehouse on every page load is slow and runs up query costs on your side, so the metadata is cached.

**Metadata refreshes automatically every 6 hours.** A table or column you create now appears in MoEngage within that window. To pick it up sooner, use **Force refresh**, which re-reads the metadata in the background.

New columns are never mapped for you. Until you map a column or mark it as skipped, it does not appear in the segment builder. Use the **Show unmapped columns** filter on the mapping screen to see only the columns still waiting on a decision.

# Edit and Delete Schemas

## What You Can Edit

You can edit descriptive details on a published schema at any time: the schema name, the event name, attribute display names, and attribute descriptions.

You cannot change the structure. Mapping columns and join columns are locked once a schema is published, because changing them would rewrite the queries behind every segment built on that schema.

## Deleting a Schema

Individual tables cannot be deleted on their own. Lookup traits can be joined in a loop, so there is no reliable last table in the chain to remove safely.

Deletion works at the schema level instead: **delete the user master schema and the whole schema for that connection goes with it** — every event table, every lookup traits table, and every join between them. To confirm, type `DELETE` in capitals.

<Danger>
  Deleting a schema breaks everything built on it. Segments that depend on it start failing, and campaigns using those segments break with them.
</Danger>

If you need a different structure, plan on recreating the schema rather than editing your way there.

# Broken Segments

When the query generated by a segment fails — because a column was renamed, a table was dropped, or a data type changed — MoEngage marks the segment **Broken** and sends an email alert.

Broken segments are listed on the All Segments page under an **Action Required** view, and the segment detail page shows a banner pointing you back to your schema configuration.

To fix a broken segment, correct the underlying schema mapping in **Warehouse Schemas**, then re-run the segment.

# Limits

| Limit | Value |
| --- | --- |
| User master tables per connection | 1 |
| Schemas per table type, per connection | 250 |
| Levels in a join path (including the user master table) | 6 |
| Attribute name length | 200 characters |
| Attribute description length | 512 characters |
| Preview rows | 5 |
| Distinct values available for filtering | 1,000 |

Schema limits are configurable. To raise them, contact [MoEngage Support](https://help.moengage.com/hc/en-us/requests/new).

# Permissions and Audit Logs

All admins can create and manage warehouse schemas. To restrict access, use [custom roles](/user-guide/settings/account/team-management/access-roles) to control which roles reach the Warehouse Schemas page.

Creating, updating, and deleting user, event, and lookup trait schemas is recorded in audit logs. Changes to the warehouse connection itself are outside this scope.

# Data Types

Warehouses use far more data types than MoEngage needs. Each column is normalized to one of six MoEngage data types, which is what determines the operators available in the segment builder.

| Warehouse data type | MoEngage data type |
| --- | --- |
| `TEXT`, `VARCHAR`, `CHAR`, and other unbounded text types | String |
| `INTEGER`, `LONG`, `DOUBLE`, `FLOAT`, and other precision numeric types | Numeric |
| `DATE`, `TIMESTAMP`, `DATETIME` | Date / time |
| `BOOLEAN` | Boolean |
| Numeric arrays | Array (numeric) |
| String arrays | Array (string) |

The mapping screen shows both types side by side — the type as your warehouse reports it, and the MoEngage type it maps to. A Redshift `VARCHAR(255)` and an unbounded `TEXT` column both become String.

Object, nested, and geospatial types are not supported. Columns using them cannot be mapped.
